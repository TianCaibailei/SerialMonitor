## 一、系统架构

### 1.1 两条捕获路径

程序提供两条**互相独立、可同时启用**的串口捕获路径：

| 维度 | 注入模式（用户态） | 驱动模式（内核） |
|---|---|---|
| 原理 | 把 hook DLL 注入目标进程，拦截其 ReadFile/WriteFile | 内核过滤驱动挂到串口设备栈，镜像 IRP |
| 覆盖范围 | **仅被注入的进程** | **全系统所有进程** |
| 权限要求 | 无（同权限即可） | 管理员 + 测试签名 |
| 串口占用 | 不占用 | 不占用 |
| 部署成本 | 每次注入 | 装一次即可 |
| 风险 | DLL 出错 = 目标进程崩溃 | 驱动出错 = 蓝屏 |

**两者互补**：注入模式零门槛即开即用；驱动模式做全系统覆盖。

### 1.2 为什么都要"不占用串口"

参考产品 CommMonitor 的驱动经逆向确认是**设备过滤驱动**：

```
IoGetDeviceObjectPointer + IoAttachDeviceToDeviceStack + IoDetachDevice  → 挂到设备栈做上层过滤
IoBuildAsynchronousFsdRequest + IofCallDriver + IofCompleteRequest       → 构造并转发 FSD 请求
ObReferenceObjectByHandle + PsGetCurrentProcessId                        → 按句柄/进程识别数据来源
```

**关键结论：驱动从不在 IRP 路径上打开串口，只是镜像 IRP。**
所以监控时业务程序仍完整独占端口 —— 这是本类软件的核心价值，两条路径都必须遵守。

### 1.3 数据流

```
        ┌──────────────── 注入模式 ────────────────┐
目标进程 ReadFile/WriteFile                        │
   ↓ 被 hook DLL 拦截（入口字节 patch）              │
monitor_hook.dll                                   │
   ↓ 命名管道 \\.\pipe\monitor_capture              │
   │   [tag u32][len u32][pid u32][payload]         │
   ↓                                               │
┌──────────────────────────────────────────────────┴────┐
│                   universal_monitor.exe                │
│  drain_capture → route_hook_data → Session::ingest     │
│  drain_driver  → ingest_driver   → Session::ingest     │
└──────────────────────────────────────────────────┬────┘
   ↑                                               │
   │  IOCTL 轮询                                    │
umserialfilter.sys（内核过滤驱动）                   │
   ↑                                               │
        └──────────────── 驱动模式 ────────────────┘
所有进程的串口 IRP
```

## 二、注入模式实现

### 2.1 组件构成

| 文件 | 架构 | 作用 |
|---|---|---|
| `monitor_hook.dll` | x64 | 注入 64 位目标 |
| `monitor_hook_x86.dll` | x86 | 注入 32 位（WOW64）目标 |
| `universal_injector_x86.exe` | x86 | 32 位专用注入器 |

**为什么 32 位需要独立注入器进程**：64 位进程向 WOW64 目标调用
`CreateRemoteThread(LoadLibraryW)` 时，即使地址和路径都正确，`LoadLibrary` 仍返回 -1。
让注入器本身是 32 位进程，所有地址天然有效。

**为什么 hoo k DLL 必须分两种架构**：PE 机器类型、指针宽度、调用约定都不同，一个二进制无法通用。

### 2.2 注入流程（64 位）

```
1. OpenProcess(PROCESS_CREATE_THREAD | PROCESS_QUERY_LIMITED_INFORMATION
               | PROCESS_VM_OPERATION | PROCESS_VM_WRITE)
2. VirtualAllocEx 分配路径缓冲区
3. WriteProcessMemory 写入 DLL 路径（UTF-16）
4. CreateRemoteThread(kernel32!LoadLibraryW, 路径)
5. WaitForSingleObject + GetExitCodeThread 确认 HMODULE 非 0
```

> `PROCESS_VM_READ` **不要**一起申请：同时带它会使得 `VirtualAllocEx`
> 在普通进程上返回 `ERROR_ACCESS_DENIED`。确实需要读远端内存时单独申请。

### 2.3 注入流程（32 位）

直接调用 `universal_injector_x86.exe <pid> <dll路径>`，由它在本机 32 位世界里完成上述步骤。

### 2.4 hook DLL 拦截了哪些 API

对**每个已加载模块**做 IAT 替换，并额外对以下函数做**入口字节挂钩**：

| 函数 | 用途 |
|---|---|
| `CreateFileW` / `CreateFileA` | 识别串口打开，建立 句柄 → 端口 映射 |
| `ReadFile` / `WriteFile` | 同步 + overlapped I/O |
| `ReadFileEx` / `WriteFileEx` | 完成例程式异步 I/O（Qt 等） |
| `GetOverlappedResult` / `Ex` | overlapped 读完成时取数据 |
| `CloseHandle` | **句柄关闭时必须清理映射**，见 2.7 |
| `GetProcAddress` | 让运行期绑定也命中钩子 |

### 2.5 入口字节挂钩（关键实现）

IAT 挂钩只覆盖"通过导入表调用"的情况。很多串口工具（尤其加壳的）在运行期用
`GetProcAddress` 自行解析并缓存函数指针，IAT 里根本没有这些函数。
**唯一可靠的兜底是改写函数入口本身。**

实测两种架构的 kernel32 桩形态（本机）：

```
x64  CreateFileW  0x7ffe28cd72c0  FF 25 E2 3C 03 00 CC CC CC ...
x86  CreateFileW  0x75dcea50      FF 25 74 12 E3 75 CC CC CC ...
```

都是 6 字节 `FF 25` 间接跳转 + `CC` 填充。挂钩实现要点：

```
target+0 .. +6   FF 25 <disp>      ; 跳到 target+8
target+8 .. +8+W 绝对钩子地址       ; W = 8(x64) / 4(x86)
```

- 指针放在桩自己的 `CC` 填充区 —— **不占用任何寄存器**
  （x64 参数在 rcx/rdx/r8/r9，x86 参数在栈上，都不能破坏）
- 操作数解析按位宽区分：
  - x64：`FF 25 rel32` → `jmp qword ptr [rip+rel32]`，rip = 下一条指令地址
  - x86：`FF 25 abs32` → `jmp dword ptr [abs32]`，操作数**就是**槽地址
- 只在前 6 字节是 `FF 25` 且其后 `+6..+8+W` 全是 `CC` 时才动手；其它形态一律拒绝
- 原目标地址存入 trampoline，钩子里通过 trampoline 调用原函数（**不能**用保存的原始指针，
  入口已被改，那个地址现在指向我们自己的跳转 → 递归）

### 2.6 串口句柄识别（关键实现）

两种来源：

1. **注入后打开**：`CreateFileW/A` 的路径直接解析出 `COM6`
2. **注入前已打开**：没有 CreateFile 事件可听，必须主动识别

第二种曾用 `GetFileInformationByHandleEx(FileNameInfo)`，**实测在串口句柄上必然失败**：

```
GetFileInformationByHandleEx(FileNameInfo) ok=0 err=87   （ERROR_INVALID_PARAMETER）
GetFileType                                = 2           （FILE_TYPE_CHAR）
IOCTL_SERIAL_GET_COMMSTATUS                ok=1          （确实是串口）
```

正确做法是**用串口专属 IOCTL 做正向判定**：

```
DeviceIoControl(h, IOCTL_SERIAL_GET_COMMSTATUS, ...)  // 只有真串口会应答
  → 成功则用 NtQueryObject 取 \Device\VSerial8_2
  → QueryDosDevice("COM6") 反查映射得 "COM6"
```

- 先做 `GetFileType` 前置过滤：`FILE_TYPE_DISK(1)` 直接排除，省掉 IOCTL
- `QueryDosDevice` 的形式必须是裸名 `COM6`；带 `\\.\COM6` 会失败
- 返回值带**尾随空格**，比较前必须 trim

### 2.7 句柄生命周期（必须处理）

钩子内部维护 `句柄 → 端口名` 映射。Windows 会**复用句柄值**，所以：

- `CloseHandle` **必须入口挂钩**（不能只靠 IAT），否则加壳程序里关闭事件永远看不到
- 关闭时删除映射；否则残留的「128 = COM6」会让后续复用该号的文件读写被误报成串口读

### 2.8 命名管道协议

```
管道名  \\.\pipe\monitor_capture
最大实例 255（每个被注入进程一条连接）
格式    [tag u32][len u32][pid u32][payload]
```

| tag | 名称 | payload |
|---|---|---|
| 1 | ATTACH | exe 路径 (UTF-8) |
| 2 | OPEN | handle u64 + 端口名 |
| 3 | CLOSE | handle u64 |
| 4 | RX | handle u64 + 字节 |
| 5 | TX | handle u64 + 字节 |

### 2.9 五条必须遵守的不变量

| # | 不变量 | 违反后果 |
|---|---|---|
| 1 | 写管道必须用**原始** `WriteFile` 指针 | 自递归死锁，目标进程卡死 |
| 2 | 诊断日志不能走 `std::fs` | 同样重入 hook 死锁 |
| 3 | 持有锁时不得写管道 | 监视端卡住会阻塞目标进程 I/O 线程 |
| 4 | Mutex 中毒必须恢复不能 unwrap | 一次 panic 带崩被监控进程 |
| 5 | 非串口句柄要负缓存 | 普通文件读写每次多一次系统调用 |

## 三、驱动模式实现

### 3.1 设备与控制接口

```
设备名      \Device\UmSerialFilter
符号链接    \DosDevices\UmSerialFilter   →  用户态打开 "\\\\.\\UmSerialFilter"
设备类型    0x8000 (FILE_DEVICE_UNKNOWN)
```

### 3.2 IOCTL 定义

| IOCTL | code | 方法 | 作用 |
|---|---|---|---|
| `IOCTL_UM_AUTHENTICATE` | 0x805 | WRITE | 提交每启动会话密钥，**必须是第一个 IOCTL** |
| `IOCTL_UM_ATTACH_PORTS` | 0x803 | WRITE | 挂接当前所有串口设备 |
| `IOCTL_UM_GET_PORT_NAME` | 0x804 | READ | 按序号取设备路径 |
| `IOCTL_UM_SET_TARGET` | 0x801 | WRITE | 设置 PID 过滤（0 = 全部） |
| `IOCTL_UM_GET_RECORD` | 0x800 | READ | 取一条记录（可阻塞） |
| `IOCTL_UM_GET_STATS` | 0x802 | READ | 读计数器（8 × u32） |

> ⚠️ `IOCTL_UM_ATTACH_PORTS` 返回值是「**本次调用新增**几个」，
> **不是**当前总数。总数请读 `IOCTL_UM_GET_STATS` 的 `attached` 字段。

### 3.3 鉴权机制

启动时生成随机会话密钥写入注册表：

```
HKLM\Software\UmSerialFilter    值名 SessionKey
```

用户态每个新句柄必须先用 `IOCTL_UM_AUTHENTICATE` 提交该密钥，否则其它 IOCTL 一律拒绝。
密钥位于只有管理员可写的键下，普通进程即使打开设备也无法驱动它。

### 3.4 记录结构

```c
#pragma pack(push, 1)
typedef struct _UM_RECORD {
    UINT32 Size;       // 头之后的负载字节数
    UINT32 Dir;        // 0=RX  1=TX  2=CTRL(串口参数)
    UINT32 Pid;        // 发起该 IRP 的进程
    UINT32 PortIndex;  // 挂接列表下标
    UINT64 Handle;     // 稳定的端口标识（不是内核指针，避免泄漏 KASLR 信息）
    UINT64 Timestamp;  // KeQuerySystemTime 换算后的 **Unix 毫秒**
    UCHAR  Data[UM_MAX_PAYLOAD];   // 4096
} UM_RECORD;
#pragma pack(pop)
```

| 常量 | 值 |
|---|---|
| `UM_MAX_PAYLOAD` | 4096 |
| `UM_RECORD_HEADER` | 32 |
| `UM_MAX_RECORDS` | 512（队列上限，超出丢弃并计数） |
| `UM_MAX_FILTERS` | 64（最多挂接设备数） |

> ⚠️ 时间戳必须输出 **Unix 毫秒**。`KeQuerySystemTime` 原生是 1601 起的 100ns 计数，
> 直接传给界面会显示成 1970-01-01。换算常量：
> `EPOCH_DIFF_TICKS = 116444736000000000ULL`，然后 `(ticks - DIFF) / 10000`。

### 3.5 串口参数（CTRL）记录

驱动额外挂接 8 个串口控制 IOCTL，在**完成例程**里读实际生效值（只读不改写）：

| IOCTL | 值 |
|---|---|
| `IOCTL_SERIAL_SET_BAUD_RATE` | 0x1B0004 |
| `IOCTL_SERIAL_GET_BAUD_RATE` | 0x1B0050 |
| `IOCTL_SERIAL_SET_LINE_CONTROL` | 0x1B000C |
| `IOCTL_SERIAL_GET_LINE_CONTROL` | 0x1B0054 |
| `IOCTL_SERIAL_SET_TIMEOUTS` | 0x1B001C |
| `IOCTL_SERIAL_GET_TIMEOUTS` | 0x1B0058 |
| `IOCTL_SERIAL_SET_HANDFLOW` | 0x1B0044 |
| `IOCTL_SERIAL_GET_HANDFLOW` | 0x1B0060 |

`CTRL` 记录用 `Dir = 2` 与数据流区分，界面显示为「设置波特率 115200」「8N1」这类行。

### 3.6 挂接实现要点

```
1. IoGetDeviceObjectPointer 取目标设备（会真的打开端口 → 端口被独占时会失败）
2. IoCreateDevice 建自己的过滤设备
3. IoAttachDeviceToDeviceStack 挂到栈顶
4. IRP_MJ_READ / WRITE / DEVICE_CONTROL 安装完成例程，只读不改 IoStatus
```

**去重**：判断"是否已挂接"必须比较**栈底物理设备**（沿 `AttachedDevice` 链一路向下），
不能比较栈顶 —— 否则每扫一次就多叠一层，每个字节被捕获 N 次。

**热插拔**：`IoRegisterPlugPlayNotification` 在 `DriverEntry` 里注册，
回调运行在系统工作线程，能覆盖驱动 RUNNING 之后才到达的设备。

## 四、端口过滤机制

### 4.1 设计原则：唯一白名单

两条捕获路径看到的世界不同（注入只看被注入进程，驱动看全系统），
但**过滤规则必须只有一份**，否则用户要在两处各勾一遍，且两处用的是不同名字。

```
唯一生效状态：Session::port_watch (HashSet<String>) + Session::port_watch_on (bool)
匹配依据：    COM 号（"COM6"），不是设备短名
生效位置：    注入路径 route_hook_data、驱动路径 drain_driver —— ingest 之前
```

两层含义：

- `port_watch_on == false` → **不限制**（默认态）
- `port_watch_on == true`  → 严格按 `port_watch` 白名单；集合为空 = 一个都不看

> 为什么需要 `port_watch_on` 这个额外开关：只用"空集合 = 不限制"无法表达
> 「取消选择（一个都不要）」，那样「全选」和「取消选择」会变成同一个动作。

### 4.2 过滤发生在"建通道之后"

被过滤的端口**仍然会建通道**，只是字节不进 `rows`。原因：通道列表就是
「监视端口」勾选区的数据源，如果被过滤的端口连通道都不建，它就永远不会出现在
列表里，用户也就没法把它勾回来 —— 单向门。

### 4.3 端口名的唯一来源

建通道和做过滤**必须用同一个函数**取名字：`ui.rs::channel_port_name()`。

```
优先：drv_com 映射出的 COM 号（用户认得的那个）
回退：设备短名（如 VSerial8_2）
```

两处名字不一致会让白名单静默失效（表现：什么都没过滤掉 / 全被丢弃）。

### 4.4 候选端口集合

「过滤设置 → 监视端口」列出：

```
会话已有的 HookSerial 通道名
  ∪  驱动已发现但还没有任何流量的端口
```

第二项很重要：某个端口还没收到数据时尚未建通道，但用户可能想**预先**把它留下、
把其它端口过滤掉。按 COM 号数字排序（COM2 在 COM10 前面）。

### 4.5 驱动侧的两种过滤层次

| 层次 | 参数 | 粒度 | 用途 |
|---|---|---|---|
| 内核 PID 过滤 | `IOCTL_UM_SET_TARGET` | 进程 | 只要某进程的流量时降低开销 |
| 用户态端口过滤 | `Session::port_watch` | 端口 | 只要某几个端口时降低噪声 |

驱动按设计挂接**全部**串口并上报一切（与参考产品一致，也让用户不必重新挂接就能切端口），
所以"只看关心的端口"由用户态完成。

## 五、界面与数据呈现

### 5.0 显示编码（决定字节如何变成文字）

捕获到的都是**字节流**，要变成用户能读的文字必须经过解码。解码入口是唯一的：

```
app/src/text_codec.rs
  DisplayEncoding { Utf8, Gbk, Utf16Le }
  decode(data, enc) -> String        // BOM 优先于所选编码
  escape_decoded(text, escape)       // 只转义控制字符，CJK 原样保留
```

**作用范围（同一解码结果贯穿全链路）**：

| 使用点 | 位置 |
|---|---|
| Table「数据」列 / 终端视图 / 详情面板 | `ui.rs` 的 `escape_text(.., enc)` |
| Dump 视图的解码文本行 | `ui.rs::view_dump`（HEX 区仍按字节，这是 dump 的定义） |
| 查找、内容过滤 | `find_next` 与 `Filters::pass(r, enc)` |
| 复制、导出日志的文本列 | `copy_selected` / `Session::save_log` |

要点：

- **UTF-16LE 必须按 `u16` 码元解码**。旧实现逐 `u8` 处理，`'A'` 会变成 `A\x00`，
  中文两字节都落在可打印区间被拆成拉丁字母 —— 这是「切了编码也没用」最极端的表现。
- **BOM 优先**：`FF FE` / `FE FF` / `EF BB BF` 开头时直接按其声明的编码解码，
  即使当前选的是别的编码。
- **导出编码与显示编码分离**：`设置→显示编码` 决定界面/检索/复制/导出的**文本内容**；
  `自动保存日志设置→文件编码` 只决定写出的**文件字节格式**（UTF-16LE 会自动写 BOM）。
- 当前显示编码常驻状态栏，并持久化在 `config.ini` 的 `displayEnc`。

### 5.6 只读定位：本软件不发送

**这是监视软件，不是串口调试助手。** 底部的详情面板只做两件事：展示选中帧的
完整内容（HEX + 解码文本 + Modbus 字段），以及把数据导出/复制出去。

早期版本有一个「发送」面板（向端口写字节、发送 Modbus 预设帧），已**整体移除**：

| 原因 | 说明 |
|---|---|
| 会污染被观测的通信 | 向正在诊断的总线注入字节，会破坏用户想看的那段对话本身 |
| 被动监听本就没有写句柄 | 「串口监听(不占用)」通道的句柄由被监控进程持有，无法写 |
| 职责错位 | 需要主动收发的场景应使用厂商调试工具，而非监控器 |

协议层的 `append_crc` / `wrap_mbap` / `build_frame` 与预设样本库**保留**，但只服务于
往返单元测试（解析器必须能把按规范构造的帧还原回来）与逆向证据留存，界面不再调用。

### 5.7 导出与复制

详情面板提供四种取出数据的方式：

| 动作 | 产物 | 用途 |
|---|---|---|
| 导出会话（.umses） | 可重新打开的存档 | 事后回看、分享给同事复现 |
| 导出日志（文本+HEX） | `session_<名>_<时间戳>.log` | 人工阅读、贴进报告 |
| 导出项目信息（JSON） | `project_info_<名>_<时间戳>.json` | 复现环境：通道配置、协议、编码、统计、过滤条件；**不含载荷字节** |
| 复制全部为 CSV | 剪贴板 | 直接粘进 Excel；受当前过滤条件约束，含表头 |

单帧层面另有「复制整行 / 复制 HEX / 复制文本」三个动作。

### 5.1 五种视图
| 视图 | 内容 |
|---|---|
| Table | 主表格：序号/时间/通道/方向/功能/长度/Hex/数据 |
| 终端 | 收发全文 |
| Dump | 字节级十六进制转储 |
| Line | 字节速率曲线 |
| Modbus | Modbus RTU/ASCII/TCP 解析 |

### 5.2 行的来源与着色

```rust
RowOrigin::Channel   // 注入 hook 或真实协议通道
RowOrigin::Driver    // 内核驱动捕获
```

| 类型 | 功能列显示 | 数据列颜色 |
|---|---|---|
| 控制记录（`rec.control`） | `设置波特率 115200` / `8N1` | `C_REQ` |
| 真 Modbus（`parsed`） | `01 请求` | 写=蓝 / 读=绿 |
| 驱动原始串口 | `串口读` / `串口写` | 写=蓝 / 读=绿 |

### 5.3 状态栏

单行显示，避免同一事件重复两处：

```
会话 1 | 通道 1 | Bytes: ↑41 ↓60 | 速率 ↑12B/s ↓340B/s | 行数 7 | 监控中 |
协议 Modbus RTU | 编码 ANSI(GBK) | <最新通知(小字)> | 驱动：未启用
```

**速率是真实字节数**：`Session::rate` 的每秒桶累加 `data.len()`（旧实现累加「行数」，
却把 Line 图的 y 轴标成 B/s）。空闲秒在图上补 0，x 轴用真实时间。
悬停速率可看最近 10 分钟的峰值。

**通知只走一处**：`Session::notices`（始终可见，小字灰色）。
`toast()` 只用于一次性确认（"已注入 xxx"），不与 notices 描述同一事件。

### 5.4 暂停语义

`Session::running == false` 时，**三条入库路径全部停止写入**：

```
注入链路   ui.rs::route_hook_data   → 检查 running
驱动链路   ui.rs::drain_driver      → 检查 running
自有通道   session.rs::poll         → 排空通道但丢弃，并清空协议重组缓冲
```

暂停期间不再累加 `bytes_rx/bytes_tx`（旧实现把被丢弃的 RX 也计入，且不区分方向），
也不保留半截的 Modbus 重组缓冲（否则恢复后会把暂停期间拼出的帧吐出来）。

### 5.5 会话存档（`.umses`）

`文件→保存会话` 写出的可重新打开的存档，`文件→打开会话` 读回。格式为 UTF-8 文本：

```
UMSEX 1
name      <会话名，制表符/反斜杠转义>
proto     <none|rtu|ascii|tcp>
encoding  <0|1|2>
views     <table,terminal,dump,line,modbus>   (各 0/1)
chan      <kind> <name> <baud> <data> <parity> <stop>
row       <seq> <idx> <dir> <secs> <millis> <hex>
```

- 行只存**原始字节**；装载时按当前解析器重建 `parsed`，因此存档不含解析器版本。
- 装载出的会话是 `running = false`，只读回看，不占用任何端口。
- 版本号不匹配或缺少 `UMSEX` 头会被拒绝并给出原因。
- `.umses` 含原始通信数据，默认被 `.gitignore` 排除。

## 七、验收测试

验收分两层，**职责不同，都要过**：

| 层 | 命令 | 证明什么 | 环境要求 |
|---|---|---|---|
| **自动化门禁** | `app\check-all.ps1` | 代码是正确的：格式、lint、32 个单元测试、双架构产物、仓库卫生 | 任意 Windows + Rust |
| **人工验收** | `app\verify-fixed.ps1` 等 | 采集链路在这个机器上是通的 | 真实/虚拟串口对、管理员 |

### 7.0 一键门禁（本地与 CI 同一套）

```powershell
cd MonitorAnything
powershell -ExecutionPolicy Bypass -File app\check-all.ps1
```

依次执行并逐项判定：

1. `cargo fmt --all -- --check`
2. `cargo clippy --workspace --lib --bins -- -D warnings`
3. `cargo test --workspace --all-targets` + **测试数量下限 30**
4. 构建 x64 主程序、x86 hook、x86 注入器，并读 PE 头校验机器类型
5. 关键文档存在且非空 + 版本库中没有私钥/证书

CI（`.github/workflows/ci.yml`）把同样的断言拆成 5 个 job 并行跑。

> **为什么要断言测试数量**：本仓库曾长期「全绿但跑了 0 个测试」——14 个测试二进制
> 里没有任何 `#[test]`。只检查退出码挡不住这种退化，所以下限是硬性断言。

### 7.0.1 自动化覆盖了什么

| 关注点 | 测试 |
|---|---|
| 解码（GBK/UTF-8/UTF-16LE、BOM、替换符） | `text_codec::tests` |

| RTU 分帧、ASCII 换行切帧、TCP 按 MBAP 长度切帧、半帧缓冲 | `session::tests` |

无法在 CI 里跑。它们仍然依赖下面的脚本——这是刻意的分工：
**CI 证明代码是对的，脚本证明这台机器上抓得到。**
