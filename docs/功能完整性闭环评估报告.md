## 〇、结论先行

**功能闭环没有完成。** 项目在「采集」这一最难的部分做得相当扎实——串口被动监听、Hook 注入、
内核过滤驱动、端口白名单这几条链路是真实现且经过实测验证的，技术手册的质量也高于一般业余项目。
但从「软件产品」的角度看，它目前更接近一个**验证过原理的高保真原型**，而不是一个可交付的软件：

- **采集层（输入端）**：✅ 基本闭环，是全项目最强的一环。
- **呈现层（输出端）**：❌ 大面积半闭环。用户可感知的「设置类控件」普遍只写字段、不接通显示。
- **会话/数据生命周期**：❌ 保存单向、不可回看、设置不落盘、状态语义自相矛盾。
- **工程质量**：❌ 零单元测试、40+ 条 dead_code 警告、私钥与二进制入库、无 LICENSE。

用户报告的那条线索——**「编码方式」切换后中文仍显示 `\xe3\xc1` 这类 `\xNN`**——属实，且不是局部 bug，
而是「呈现层根本没有解码能力」这一系统性缺陷最典型的症状。详见第二章。

| 维度 | 评级 | 一句话 |
|---|---|---|
| 采集能力（Hook / 驱动 / 端口过滤） | A- | 逆向扎实、链路打通、有实测证据 |
| 协议解析（Modbus RTU/ASCII/TCP） | B- | 有实现，但有组帧/校验 Bug 与文档数字不符 |
| GUI 控件闭环 | D | 大量控件「点了没反应」或「只作用一半」 |
| 会话与文件 | D | 保存不可回看，设置不持久化 |
| 测试与可重复验证 | F | 14 个测试二进制、0 个测试 |
| 工程规范 / 可交付性 | D- | 私钥入库、无 LICENSE、仓库 9.5GB |
| 文档质量 | A- | 技术手册详尽、诚实，但部分宣称偏乐观 |

## 一、评估判据：什么叫「功能闭环」

本报告对每个用户可见控件使用同一把尺子：

> **闭环 = 控件改变状态 → 有真实下游消费者 → 用户可感知到结果 → 结果可持久化/可重复验证。**

按此判据分为四档：
- ✅ **闭环**：链路完整，行为符合控件名称的语义。
- ⚠️ **半闭环**：有下游，但作用域窄、语义不符、或只覆盖部分路径。
- ❌ **摆设 / 缺失**：无消费者、对主链路无效、或功能根本不存在。
- ❓ **存疑**：依赖特定运行环境，本机无法验证。

### 2.3 发送面板（ui.rs:1603-1729）

**这是「控件看起来能用、实际必失败」的最典型例子。**

- `Session::send_bytes()`（session.rs:990-1029）确实真的写出：串口 `write_all` (997)、TCP 所有连接
  `write_all` (1000)、UDP `send_to` (1018)，成功后回灌 `ingest(..., true)` (1026) 让 TX 行可见。
- **但 `ChanKind::HookSerial` 分支恒返回 `Err("拦截通道只读…")` (1022)。**
- 而默认通道类型就是 `chan_kind=0` → `CHAN_KINDS[0]="串口监听(不占用)"` → `HookSerial` (448)，
  `Session::new` 对 HookSerial 不 open 任何可写句柄 (400 空分支)。
- ⇒ **用户最常见的默认配置下，整个发送面板 100% 失败**；错误只 `push` 到 `s.notices` (1672)，
  状态栏只显示最后一条 (1156)，按钮始终 enabled、无就近提示。
- 附带实锤 Bug：「发送预设」的 ASCII 组帧（ui.rs:1704-1711）把 **LRC 追加了两次**
  （十进制串 + 十六进制串），`parse_ascii_text` (protocol.rs:159) 校验必失败，发出的是坏帧。

### 2.5 用户报告缺陷的完整根因（重点）

**症状**：切换「编码方式」（UTF-8 / ANSI(GBK) / Unicode(UTF-16LE)）对监控内容显示无实质影响，
中文仍显示成 `\xe3\xc1` 这类 `\xNN`。

**根因：仓库从来不具备「按编码解码字节流」的能力。**

三个编码字段全部只活在「导出文件」路径上：

| 字段 | 定义 | 赋值 | 唯一消费者 | 实际效果 |
|---|---|---|---|---|
| `save_enc`（菜单 设置→编码方式） | ui.rs:83 | 1092-1093 | `save_active` (923) → `save_log` (session.rs:1041) | 只决定手动导出 `session_N.log` 的字节编码 |
| `r_enc`（自动保存对话框 ComboBox） | ui.rs:204 | 2782 | `Autosave.encoding` (530/2797) | 只决定自动保存文件编码 |
| `Autosave.encoding` | session.rs:233 | — | `autosave_line` (1098-1108) | `encoding_rs::GBK.encode` / `UTF_16LE.encode` |

`encoding_rs`（Cargo.toml:12）全仓只有 **4 处 `.encode()`**（session.rs:1059/1063/1100/1104），
**零处 `.decode()` / `new_decoder()`**。

更关键的是：`save_log` (1049-1055) 与 `autosave_line` (1091-1097) 输出的正文是 `bytes_hex(&r.data)`
——纯 ASCII 十六进制文本。编码选择实际只影响表头「# 万能监控日志 v1」和方向字「读/写」这几个
中文字符的字节表示，**对监控内容连「导出」都谈不上影响**。

**所有「按字节显示」的调用点（已穷举）**：

| 位置 | 行为 |
|---|---|
| `escape_text` (session.rs:332-350) | `for &b in data`；`\r/\n/\t`→转义串；`(0x20..0x7F)`→字符；其余→`\x{:02X}` 或 `?`。**逐字节，无编码概念** |
| ui.rs:1375 / 1412 / 1638 | Table「数据」列 / 终端每行 / 发送详情，均 `escape_text` |
| ui.rs:1467 | Dump ASCII 侧栏内联逐字节判断 |
| ui.rs:944、session.rs:151 | `String::from_utf8_lossy` 用于 `find_next` 与 `Filters::pass` |
| ui.rs:1565-1569 | Modbus Values 逐字节（数值语义，合理） |

所以 GBK「中」=`D6 D0` → `\xD6\xD0`；UTF-8「中」=`E4 B8 AD` → `\xE4\xB8\xAD`。
用户看到的 `\xe3\xc1` 正是这类逐字节转义。**五种编码切换在界面上只改变 `\xNN` 的个数/组合。**

**UTF-16LE 还有额外破坏**：`escape_text` 的循环单位是 `u8` (334)，而 UTF-16LE 每个码元 2 字节：
`'A'` = `41 00` → `A\x00`；`'中'` = `2D 4E` 两字节都落在 `0x20..0x7F`，被当成两个 ASCII 字符输出 `-N`。
全仓无任何按 `u16` 组码元解码的逻辑，也无 BOM 检测。⇒ 选 UTF-16LE 连纯英文都会掺入 `\x00`。

**影响面超出显示**：
1. 检索层同样失效（`find_next`、`Filters::pass` 都用 `from_utf8_lossy`）——只修渲染，中文仍搜不到。
2. 复制与导出只给 HEX（ui.rs:979、session.rs:1054/1096）——「保存中文日志」这条路本身不存在。
3. 两个编码控件语义混淆（一个叫「设置→编码方式」管手动导出，一个藏在「自动保存」里），
   用户极易误以为前者管显示。
4. 都不持久化（`save_cfg` 415-429 只写 9 个键）、界面无当前值提示、菜单 radio 点击不 `close_menu()`。
5. UTF-16LE 导出无 BOM（session.rs:1068 / 1109），多数编辑器会误判为 ANSI。

**修复方向**：新增 `decode_text(data, enc) -> String`（GBK decoder / UTF-16LE 按 `u16` 码元 + BOM /
UTF-8 lossy）；把「显示编码」提升为会话级字段，与「导出编码」显式分离并在 UI 说明；让
`escape_text` 接收解码后的 `String`；同步改造 `find_next` / `Filters::pass` / `copy_selected` / 导出；
编码落盘并在状态栏显示当前值。

### 2.6 GUI 层最严重的 8 个问题（按用户可感知程度排序）

1. **「编码方式」是全局性假控件，中文监控内容永远不可读**（见 2.5）
2. **「暂停监控」对默认且主要的捕获路径完全无效**，状态栏显示「已暂停」而数据继续入行
3. **保存单向不可回看**，「打开会话」整个缺失，硬编码文件名会静默覆盖
4. **默认会话的「发送/发送预设」必失败**，且按钮不禁用、无就地提示；ASCII 预设帧是坏帧
5. **查找半残**：找不到中文、命中不滚动定位、「查找」与「查找下一个」是同一函数
6. **三个设置对话框只对 active 会话生效、无会话时静默无效、不回显、不落盘**
7. **Line 图把帧数当 B/s、状态栏完全没有速率**；`string_len` 名不副实、`merge_ms` 对驱动路径无效
8. **关闭会话不停止应用级捕获，会话会「自己长回来」**；Modbus 视图在原始数据/驱动行下永远空白

### 3.2 协议解析（app/src/protocol.rs）

协议层有真实实现（CRC-16/MODBUS 按位计算、LRC、RTU/ASCII/MBAP 解析、请求/响应预设库），
但存在几处实证问题：

- **MBAP 组帧与解析不自洽**：`wrap_mbap` (249) 把整个 `pdu`（含 uid）塞进 MBAP 后，
  `len = pdu.len()+1`；而 `parse_mbap` (194) 期待 `buf[6]=uid, buf[7]=fc`。
  发送端「发送预设」造出的 TCP 帧，接收端按自己的解析器理解不了。
- **预设数量与注释/文档不符**：注释声称 23 请求 / 43 响应（protocol.rs:264/291），
  实测代码为 **24 / 38**；上级 README:20 沿用了「23 请求 + 43 响应」。
- **ASCII 组帧坏帧**（ui.rs:1704-1711，LRC 追加两次），见 2.3。
- `parse_ascii_text` (159) 用 `from_utf8_lossy` + 过滤 hexdigit，对非 ASCII 字节容错但未报错。
- 边界：RTU 帧仅 `len>=4` 检查，`bufs` 重组用 `>=600` 强制 flush，长帧/粘包策略偏启发式。

### 3.3 会话与数据模型

- `Session::ingest` (804) 按 `proto` 分派 RTU/ASCII/TCP 帧重组，`push_row` (907) 实现
  `merge_ms` 合并；`Filters::pass` (130) / `port_allowed` (440) 在渲染与 ingest 两处生效。
- **`ingest_driver` (738-802) 直接 push row，绕过 `push_row`** ⇒ 合并设置对驱动数据无效，
  两套入库路径行为不一致。
- **`running` 语义割裂**：`poll()` (690) 在暂停时丢弃数据却仍 `bytes_rx += data.len()` (695)，
  且该分支不区分方向，TX 被计入 RX；而 hook/driver 主链路根本不查 `running`。
- **保存是导出而非会话文件**：`save_log` (1041) 只写 HEX 文本；无反序列化、无格式版本、无元数据。
- `notices` 无界增长风险（ui.rs:2903 仅在 auto-attach 路径裁剪到 64）。
- 主程序有 **14 处 `unwrap()`**（session.rs:558/620/662/722/725/726/822/829/850/853/877/882/1001、
  inject.rs:362、main.rs:122/127），其中 `tcp_writes.lock().unwrap()` 在连接线程里。
  技术手册「五条必须遵守的不变量」第 4 条明确要求「Mutex 中毒必须恢复不能 unwrap」——
  **该约束在 hook DLL 侧被遵守，主程序侧没有**。

### 3.4 驱动与注入

- 驱动部分是全项目质量最高的模块：会话密钥鉴权（HKLM 只读键）、记录队列上限、
  Unix 毫秒时间戳、热插拔 PnP 通知、去重按栈底物理设备、8 个串口参数 IOCTL 的完成例程只读镜像。
- archive 里历史严重问题（卡死、崩溃、幽灵读、句柄复用、注入后无捕获、附加 0 个串口）
  均有根因与修复记录，且多数能在当前代码找到对应防护；技术手册把结论收编得较完整。
- 残余风险：驱动部署依赖测试签名 + 管理员 + WDK + 透明加密软件解密，
  **换一台机器无法一键复现**；`umfilter-test.pfx`（含私钥）已入库，见 3.6。

## 四、以「优秀软件」为标准的差距清单（按阻碍程度排序）

### P0 —— 不修就不能称为「可用产品」

1. **建立解码层，让「编码方式」真正生效**（2.5）：会话级显示编码 + `decode_text` +
   渲染/查找/过滤/复制/导出全链路按解码文本工作 + UTF-16LE 按 `u16` + 导出 BOM + 落盘 + 状态反馈。
2. **统一 `running` / 暂停语义**：hook、driver、poll 三条入库路径统一门禁；
   明确「冻结视图」与「停止入库」的区别；暂停时 Bytes/Line 口径一致。
3. **默认会话的发送面板**：按通道类型禁用并就地说明「监听模式只读」，
   或提供明确的切换到独占用会话的入口；修正 ASCII 预设帧 LRC 双追加。
4. **会话可回看**：定义版本化会话格式（rows + 通道 + 时间 + 解析结果 + 编码 + 过滤），
   实现「打开会话 / 另存为 / 文件对话框 / 最近文件」，去掉硬编码覆盖。
5. **设置全量落盘 + 回显 + 取消回滚 + 区分全局默认/会话实例**，消除「保存了但重启就没了」。

### P1 —— 决定「好不好用」

6. **查找可用化**：解码文本/正则/HEX 多模式、命中列表与上下导航、`scroll_to_row` 定位、命中计数。
7. **Line 图与速率真实化**：`rate` 累加字节数、按真实秒建桶补零、状态栏加实时/峰值 B/s。
8. **设置语义对齐**：`string_len` 要么真正作用于文本列要么改名并标注作用域；
   `merge_ms` 让驱动路径也走统一 `push_row`；`p_scroll` 单源。
9. **视图与会话生命周期**：运行期增删/重排视图、关闭会话时明确处置后台捕获、
   Modbus 视图对无解析行给空态说明、视图全取消显示空态。
10. **协议层自洽**：统一 `wrap_mbap` / `parse_mbap` 的 MBAP 语义，校正预设数量与文档，
    给 ASCII/RTU 组帧加校验与单元测试。

### P2 —— 决定「能否交付 / 能否长期维护」

11. **补真正的测试**：给 `protocol.rs`（CRC/LRC/三种解析/组帧往返）、`session.rs`
    （Filters、port_allowed、merge、ingest 分派）、`escape_text`/新解码层写 `#[test]`；
    把 `verify-*.ps1` 的验收点转成可重复的自动化断言；加 CI。
12. **清理调试残留**：移除或 `#[cfg(test)]` 化 14 个探针、合并
    `native_serial*.rs`、消除 40+ dead_code 警告与「future hard error」。
13. **安全与仓库卫生**：把 `umfilter-test.pfx` 移出版本库并轮换、清理已入库 `.sys`、
    补 LICENSE（并明确与参考产品的合规边界）、补 CHANGELOG、修 .gitignore 乱码与空 Cargo.toml。
14. **可移植构建**：去掉硬编码绝对路径、把字体/WDK/透明加密解密步骤写成带检测的脚本、
    产出安装包与卸载、补首次运行向导与应用日志。
15. **仓库拆分**：把 `craft-anything` / `craft-fonts*` / `build_check` 移出交付仓库，
    让 `MonitorAnything` 成为独立、体积合理、可 clone 即构建的仓库。

### P3 —— 从「够用」到「优秀」

16. 数据：导出 CSV/JSON/原始二进制/选中范围、会话对比、书签与备注、正则过滤预设。
17. 视图：列显隐/排序/宽度、并排拆分、主题/字体/DPI、虚拟滚动与行数上限提示。
18. 发送：定时/循环发送、转义解析、按编码发送文本、发送历史、自定义预设库。
19. 协议：自定义解析器/插件、多协议自动识别、字段树、寄存器值解释（浮点/有符号/字节序）。
20. 可用性：快捷键、工具提示、匹配触发与告警、错误帧计数、多语言、无障碍、链路健康指示。

## 五、值得肯定的部分（避免只列问题）

- **逆向与设计文档质量很高**：`docs/技术手册.md` 614 行，把两条捕获路径、入口字节挂钩的
  汇编级细节、句柄生命周期、IOCTL 语义陷阱、端口白名单「唯一生效状态」都写清楚了；
  `investigation.cany/` 保留了证据账本。多数项目做不到这一点。
- **最难的技术点真做出来了**：不占用串口的被动监听、x86/x64 双架构注入、
  内核过滤驱动的 IRP 镜像，且 `verify-no-steal.ps1` / `verify-fixed.ps1` 有实测结论。
- **历史 bug 有根因记录**：archive 里「卡死」「幽灵读」「句柄复用」「附加 0 个串口」
  等都有「现象→实测→根因→修复」的闭环，不是改完就算。
- **端口白名单是全项目最完整的一条闭环**：从对话框草稿 → `port_watch` → 在 ingest **之前**
  于 hook/driver 两条路径同时生效，且考虑了「过滤后仍建通道以便勾回来」这种细节。
- **驱动失败时的用户引导**：状态栏区分「未启用/未安装」并指路，`dlg_driver_ui` 给完整安装命令。

## 六、下一步建议（如果只做三件事）

1. **先修「编码方式」**（2.5 的修复方向）——它是用户主动报告的、影响面最大、
   且能顺带把检索/复制/导出一起理顺的一条主线。
2. **再统一三条入库路径的状态门禁**（`running`、合并、计数）——消除「界面说暂停、数据照样进」
   这类自相矛盾，这是「软件是否可信」的分水岭。
3. **补 20~30 个单元测试 + 清掉调试残留 / 私钥 / LICENSE**——把这从「跑通过一次的项目」
   变成「别人 clone 下来能构建、能验证、敢分发」的软件。

> 一句话：**采集层已达 A 级，呈现层与工程层还在 D 级。**
> 闭环的断点不在「能不能抓到数据」，而在「抓到之后，用户能不能按自己设置的方式看懂、找得到、
> 存得下、下次还能打开」。
