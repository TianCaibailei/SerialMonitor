# 关闭程序时的「幽灵读」—— 根因与修复

> 2026-11-11 · 对应 `app/tests/handle_reuse.rs`

## 现象（用户报告）

在串口助手中先关闭串口、再关闭程序时，监视软件会**偶发**跳出一条「读」记录，内容是：

```
1794393325=0,5
1794393306=0,4
1794393304=0,3
1794393302=0,2
1794393300=0,1
1794393237=0,Welcome to UartAssist3
1794393228=0,Welcome to UartAssist2
1794388567=0,Welcome to UartAssist1
...
```

而这段时间通过串口实际只发过单字符 `1、1、2、3、4、5、8、9`。

## 关键判据

那条内容的格式是 `时间戳=0,内容`，**这不是串口上流动的字节**，而是串口助手自己的
**数据日志文件**的内容（`=0,5`、`=0,4` 正好对应发过的单字符 5、4）。

也就是说：**一次普通文件读取，被误报成了串口读。**

## 根因：句柄被复用 + 关闭事件从未被观察到

两个缺陷叠加才产生这个现象。

### 缺陷 1：`CloseHandle` 只靠 IAT 挂钩，对该目标永远不生效

`patch_entries` 原本只对 6 个函数做入口挂钩：

```
CreateFileW / CreateFileA / ReadFile / WriteFile / ReadFileEx / WriteFileEx
```

`CloseHandle` **不在其中**，它只有 IAT 挂钩。而 UartAssist 是 UPX 加壳、运行期用
`GetProcAddress` 自行绑定，实测它的导入表里这些函数**一个都没有**：

```
CloseHandle    in IAT: False
ReadFile       in IAT: False
WriteFile      in IAT: False
CreateFileW    in IAT: False
CreateFileA    in IAT: False
```

所以 `hook_CloseHandle` 在这个进程里**从未执行过**。

后果不是"少一条日志"这么轻。钩子内部维护 `HANDLES: handle -> "COM6"` 这张表，
用来把读写的字节归到对应串口。句柄关闭时本该删掉对应项，现在删不掉 ——
**那张表里的串口条目永久残留**。

### 缺陷 2：Windows 会复用句柄值

句柄值只是当前进程句柄表里的一个序号。串口关掉后，同一个数字很快会被下一个打开的
对象拿走。而此时表里还留着「128 = COM6」这条**过期记录**，于是：

被复用的文件读写的字节 → 查表命中「COM6」→ 上报为该串口的读。

关闭程序时它会写/读自己的日志文件，这正是那条幽灵读的来源，也解释了为什么
「关闭串口后、关闭程序时」才触发。

## 实测复现

`app/tests/handle_reuse.rs` 精确复现了这个前提：先开串口、记下句柄值、关掉，
然后反复打开普通文件直到**拿到同一个句柄值**，再通过它写入一段带标记的内容。

实测输出（修复后）：

```
serial: COM6 open handle=0x128 GetFileType=2
serial: closed (a correct hook must now forget this handle)
file:   REUSED the serial handle value handle=0x128 GetFileType=1
file:   wrote 52 bytes through the reused handle
result: reproduced a handle-value collision (this is the bug's precondition)
```

钩子日志里能直接看到同一个 `0x128` 先被 `\\\\.\\COM6` 占用、随后被普通文件拿走：

```
createfilew: "\\\\.\\COM6"                                  -> h=128
cfw: \\.\COM6 -> h=128
...
createfilew: "...\hreuse_9.txt"                             -> h=128
```

## 修复

### 1. 把 `CloseHandle` 纳入入口挂钩（根本修复）

`patch_entries` 从 6 个函数扩展到 **7 个**，加入 `CloseHandle`。这样无论目标是怎么
拿到函数地址的，关闭事件都会被看到，`HANDLES` 里的条目会被正确移除。

```
inline CreateFileW / CreateFileA / ReadFile / WriteFile /
       ReadFileEx / WriteFileEx / CloseHandle   → 7/7 全部装上
```

`hook_CloseHandle` 同时改为走 trampoline（`orig_call_addr`），否则入口被改后会自递归。

### 2. 用 `GetFileType` 前置过滤，把普通文件挡在最前面

即使句柄被复用，也不该对一个**磁盘文件**发串口 IOCTL。实测分类可靠：

```
COM6 串口     GetFileType = 2 (FILE_TYPE_CHAR)
win.ini 文件  GetFileType = 1 (FILE_TYPE_DISK)
```

所以 `probe_serial_port` 第一步就判断：

```rust
if GetFileType(h) == FILE_TYPE_DISK {
    return None;   // 磁盘文件不可能是串口，连 IOCTL 都不发
}
```

这是**双保险**：即使将来某个句柄复用路径又漏了，磁盘文件也不会被当成串口。

### 3. 顺带修掉 `dbg_note` 的同类隐患

`dbg_note` 里 `close` 原来直接用 `ORIG_CLOSEHANDLE` 保存的原始地址。`CloseHandle`
一旦被入口挂钩，那个地址就指向我们自己的跳转，调用它会从诊断写日志的路径里
**重入 hook_CloseHandle**。已改为走 trampoline。

## 验证

`verify-fixed.ps1` 全绿（32/64 位「先开端口后注入」均 PASS，驱动连跑两次都是 4 个端口），
且修复后该探针的日志里，文件句柄 `0x128` **不再被判定为串口**（串口探测命中次数 0）。

## 遗留说明

这条幽灵读需要「句柄值恰好被文件复用」才出现，所以是**偶发**的 ——
和用户描述的"偶发性"完全吻合。修复后即使碰撞再次发生也不会误报，但请注意：

- 本次是**用户态注入**方案的修复。如果走内核驱动路径，驱动在 IRP 层工作，
  不依赖用户态句柄表，不存在这个问题。
- `HANDLES` 仍然是进程级缓存。若目标程序长期运行、频繁开关串口，建议仍保留
  入口级 `CloseHandle` 挂钩（现在已是默认行为）。
