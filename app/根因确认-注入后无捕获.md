# 注入后无法捕获串口读写 —— 根因与修复

> 2026-11-11 · 对应 `verify-fixed.ps1` PASS（32 位 / 64 位均通过）

## 一、你报告的现象

> 打开串口助手 → 打开监视软件 → 启用监视并注入串口助手进程 → 在串口助手中打开串口 → 发送消息
> → **监视端看不到任何内容**

我用 32 位探针复现了它，并定位到**三个独立缺陷**。三个都必须修，少一个现象依旧。

---

## 二、根因 A：32 位目标上一个 IAT 都没打上（`patch_iat` 拒绝 PE32）

### 实测

`app/hook/src/lib.rs` 里 IAT 解析函数原本这样写：

```rust
let opt = base.offset(e_lfanew).offset(0x18);
if *(opt as *const u16) != 0x20B {
    return; // PE32+ (x64) only
}
let imp_rva = *(opt.offset(112 + 8) as *const u32) as isize;
```

`0x20B` 是 **PE32+（64 位）**的 optional-header magic。而**32 位进程里每一个模块都是 PE32（`0x10B`）**，
所以注入到 WOW64 目标后，`patch_iat` 对**每个模块**都在第一行 `return` 了 —— 一个导入项都没改。

探针证据（修复前）：

```
inject-test: 32位(WOW64) = Some(true)   ← 注入成功
inject-test: 模块已加载 = true          ← DLL 确实在里面

um_hook_10636.log:
  pipe connected
  patched        ← patch_all 跑完了
  worker ready
```

探针随后成功打开 COM1、写入 6 字节，但日志里**没有 `cfw:`（CreateFileW 钩子没被调用）**，
监视端 0 条记录。「注入成功 + 日志正常 + 一个字节都抓不到」就是这么来的。

### 修复

导入目录在 OptionalHeader 里的偏移随 magic 变化，必须按镜像自己的 magic 取：

| magic | 含义 | DataDirectory[1] 偏移 |
|---|---|---|
| `0x20B` | PE32+ (x64) | 112 + 8 = 120 |
| `0x10B` | PE32 (x86) | 96 + 8 = 104 |

`usize` 表项宽度不用改：x86 的 hook DLL 是独立 crate 单独按 i686 编译的，`usize` 天然 4 字节。

## 三、根因 B：UartAssist 是 UPX 加壳 + 纯动态绑定，IAT 挂钩对它永无效果

你用的 `D:\UartAssist.exe` 实测：

```
UPX0  va=001C7000 vs=1C7000 rs=0     char=E0000080        ← 解压目标区，磁盘上没有内容
UPX1  va=001C8000 vs=9C000  rs=9BA00 char=E0000040 熵=8.00 ← 压缩后的真实代码

KERNEL32.DLL 导入表只有 4 个函数：
  LoadLibraryA, ExitProcess, GetProcAddress, VirtualProtect
```

它**根本没有导入 `CreateFileW` / `ReadFile` / `WriteFile`**。
运行期用 `GetProcAddress` 自己解析并缓存函数指针，而且**解析发生在我们注入之前**。所以：

| 手段 | 对它是否有效 | 原因 |
|---|---|---|
| IAT 挂钩 | ❌ | 导入表里没有这些函数，没有可改的项 |
| `GetProcAddress` 挂钩 | ❌ | 只影响注入之后的解析，它早就解析完了 |
| **函数入口字节挂钩（inline）** | ✅ | 不管调用方怎么拿到地址，入口被改了就是会跳到我们这里 |

这正是原版 CommMonitor 用内核驱动的原因之一：驱动在 IRP 层，与用户态怎么绑定函数无关。

### 修复

1. **入口挂钩改为默认启用**。原来它藏在 `%TEMP%\um_hook_inline` 标记文件后面（默认关闭），
   而它是唯一能覆盖这类目标的手段 —— 默认关闭等于对加壳程序完全不工作。
2. **支持 32 位**。原实现只写 x64 编码：
   - 补丁指令 `48 B8 <imm64> FF E0`（`mov rax, imm64; jmp rax`）在 32 位进程里是非法编码
   - `FF 25` 的操作数解析写死成 `[rip+rel32]`，而 32 位的 `FF 25` 是 `jmp dword ptr [abs32]`

   实测两种架构的 kernel32 桩形状：

   ```
   x64  CreateFileW  0x7ffe28cd72c0  FF 25 E2 3C 03 00 CC CC ...
   x86  CreateFileW  0x75dcea50      FF 25 74 12 E3 75 CC CC ...
   ```

   两者都是 6 字节 `FF 25` + int3 填充，但操作数含义不同。现在按 `usize` 宽度分别处理，
   补丁本身也改成「把钩子指针写进桩自己的 int3 填充区，再 `FF 25` 跳过去」——
   不占用任何寄存器（x64 参数在 rcx/rdx/r8/r9，x86 在栈上，都不能被破坏）。

3. **顺手修掉两个真实缺陷**：
   - 原 trampoline 分配 `patch_len + 16` 字节，却往 `tramp + patch_len + 12` 写 8 字节指针（越界 4 字节）
   - 原实现通过 trampoline 里的指针做 RIP 相对跳转，要求 `VirtualAlloc` 返回地址在 kernel32 ±2GB 内
     —— 实测经常不在，所以长前缀的分支基本不可用

4. **修掉启用后的自递归**：`CreateFileA` / `ReadFileEx` / `WriteFileEx` 的钩子原来直接调用
   `ORIG_*` 保存的原始地址；入口被改后那个地址指向我们自己的 `jmp`，会无限递归。
   现在统一走 trampoline（`orig_call_addr`）。

实测（修复后，真实 UartAssist，PID 18852）：

```
inline CreateFileW: trampoline=0x66c0000
inline CreateFileA: trampoline=0x66d0000
inline ReadFile:    trampoline=0x66e0000
inline WriteFile:   trampoline=0x66f0000
inline ReadFileEx:  trampoline=0x6700000
inline WriteFileEx: trampoline=0x6710000
worker ready
→ 6/6 入口全部装上
```

## 四、根因 C：`com_label` 在串口句柄上必然失败（这一条最隐蔽）

前两条修好后，探针在「先注入、后开端口」下已经能抓到了，但**你报告的顺序仍然抓不到**。
因为你的顺序是「串口助手先打开端口，我们再注入」—— 这时端口句柄**在注入前就存在**，
没有 `CreateFileW` 事件可听，只能靠 `com_label` 事后识别句柄。

而 `com_label` 用的是：

```rust
if GetFileInformationByHandleEx(h, FILE_NAME_INFO_CLASS, ...) == 0 {
    return None; // 注释认为这是"瞬时失败，不缓存"
}
```

### 实测：这个调用在串口句柄上**永远**失败

我写了一个探针直接问系统（`app/tests/serial_name.rs`）：

```
GetFileInformationByHandleEx(FileNameInfo) ok=0 err=87     ← ERROR_INVALID_PARAMETER
GetFileType                          = 0x2 (FILE_TYPE_CHAR)
IOCTL_SERIAL_GET_COMMSTATUS          ok=1                  ← 确实是串口
```

两种架构都一样。于是：

1. `com_label` 永远返回 `None`
2. 失败路径**故意不写负缓存**（怕把正常句柄误判成非串口）
3. 结果**每一次 I/O 都重新探测、重新失败、然后把字节丢掉**

现象就是：注入成功、`WriteFile` 钩子确实被调用（我用日志确认过 `wf: enter h=c4 len=5` 有 25 条），
但监视端一条都没有。

### 修复

改成用串口 API 自己来判定，而不是问文件名：

```
DeviceIoControl(h, IOCTL_SERIAL_GET_COMMSTATUS, ...)
```

只有真正的串口才会应答这个 IOCTL —— 控制台、管道、普通文件都不应答，
所以它是**正向、无歧义**的判定（`FILE_TYPE_CHAR` 不行：conhost 的句柄也是这个类型）。

拿到设备路径后再用 `QueryDosDevice` 翻译成用户认得的 COM 号。实测这个 API 的形式很容易搞错：

```
QueryDosDevice("COM1")      -> "\Device\VSerial8_0"   ✅
QueryDosDevice("\\.\COM1")  -> 失败                    ❌   （原实现如果这么用就会静默失败）
```

（返回的设备名还带一个尾随空格，必须 trim，否则字符串比较永远不相等。）

修复后的日志：

```
com_label: h=100 串口探测命中 COM6
```

## 五、顺带修掉的：驱动「附加到 0 个串口」的谎报

`--driver-test` 一直打印「附加到 0 个串口设备」，但**驱动其实一直附加着 4 个端口、捕获完全正常**。

根因：`IOCTL_UM_ATTACH_PORTS` 的返回值语义是「**本次调用新增**几个」，
而所有用户态调用方都当成「**当前总共**几个」用。首轮扫描附加完 4 个之后，
此后每次扫描都走「已附加」分支，返回值恒为 0。

实测证明（`app/tests/stats_probe.rs`）：

```
[附加前] 已附加=4
probe: ATTACH_PORTS ok=1 ret=4 本次新增附加=0
[附加后] 已附加=4
```

即：驱动报的**改完之后**是 `ok=1 ret=4`，修复后连续两次都是 4。
修复点：`app/src/driver.rs` 的 `attach_ports()` 改为从 stats 读总数（驱动本来就在正确维护它），
只在 stats 不可用时才退回用增量。

**注意验证方法**：必须连续跑两次 `--driver-test`。重装驱动后第一次会从 0 数到 4，
看起来像"修好了"，第二次才是真相。

## 六、端口过滤设置（新功能）

你说「规划的通过端口进行过滤设置的目前还没有实现」——确认此前确实没有，现在补上了。

- **`过滤设置`对话框新增「监视端口」区**：列出该会话所有串口通道，checkbox 勾选，
  带 全选 / 反选 / 取消选择。
- **两条数据路径都生效**：注入(hook)路径的 `route_hook_data` 和驱动路径的 `drain_driver`
  都在把字节喂进会话**之前**调用同一个 `Session::port_allowed(端口名)`，
  所以被取消勾选的端口是**根本不进会话**，不是界面上隐藏。
- **持久化**到 `config.ini`（会话级）。
- **设计要点**：比原来的 `drv_watch` 多了 `port_watch_on` 开关。原因是 `drv_watch` 用
  「空集合 = 不限制」表达默认态，这样无法表达「取消选择（一个都不看）」——
  不加开关的话「全选」和「取消选择」会变成同一个动作。
- 过滤点放在**建通道之后**：被过滤的端口仍然会建通道，所以它还在「监视端口」列表里，
  用户随时能勾回来，不会变成单向门。

## 九、遗留与建议

| 项 | 状态 |
|---|---|
| 内核驱动全系统捕获（不注入） | 驱动本身工作正常（已实测 31 条记录 / TX 62 / RX 684 字节），但需要管理员加载 |
| 驱动对「端口被独占」的重复附加 | COM6/COM7 被程序独占时 `IoGetDeviceObjectPointer` 会失败，驱动没有对应计数器，属于诊断缺失 |
| 数据顺序合并（同端口同方向的多次读合并成一行） | 等你决定是否启用 |

### 使用建议

现在入口挂钩默认启用，所以**不再要求「注入必须先于打开端口」**。
正常流程即可：打开监视软件 → 附加到串口助手 → 在串口助手里打开端口收发。

如果仍然抓不到，按这个顺序排查（都能从 `%TEMP%\um_hook_debug` 标记文件 + 日志看清）：

1. `%TEMP%\um_hook_<pid>.log` 里有没有 `inline CreateFileW: ...`？没有 → 入口挂钩被拒绝（贴日志给我）
2. 有没有 `com_label: ... 串口探测命中 COMx`？没有 → 该句柄不是串口，或端口号映射没读到
3. 有没有 `createfilew: "\\.\COMx"`？没有 → 程序打开端口用的不是 CreateFileW/A
