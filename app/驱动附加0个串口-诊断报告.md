# 驱动「附加到 0 个串口」诊断报告

> 2026-11-11 · 只读调查 · 未修改驱动源码，未停止/重装驱动，未运行 rebuild-all.ps1 / install-driver.ps1

---

## 0. 一句话结论

**驱动其实一直好好地附加着 4 个端口、也一直在正常捕获，`--driver-test` 里那句「附加到 0 个」是一句谎报。**

根因：`IOCTL_UM_ATTACH_PORTS` 的返回值被 `UmAttachAllPorts()` 实现成「**本次调用新增**了几个」，而全部用户态调用方都把它当成「**当前总共**附加了几个」来用。端口在第一次扫描时就已经全部附加完，此后每次扫描都是「新增 0 个」，于是进程稳定打印 0、随后又用 0 去查端口名，自然拿到空表。

**这不是驱动没跑，也不是二进制与源码不一致 —— 恰恰相反，实测证明运行中的二进制就是当前源码、而且捕获链路完全正常。**

### 1.4 运行中的 `.sys` 就是当前源码编译产物（**推翻文档里的「旧二进制」说法**）

`driver\三个问题的回答与新发现.md` 第 130-132 行断言：

> 当前运行的驱动是 **15:43 编译的 23,944 字节版本**，而最新代码是 **23,040 字节**。
> **运行中的是旧二进制**，行为与新代码不一致。

实测**否定**这个说法：

```
umserialfilter.sys      size=24456  sha256=6FEC0BCC…  peTime=0x6AF42C30 => 2026/11/11 16:49:52
umserialfilter_x64.sys  size=23040  sha256=2B9CCE4C…  peTime=0x6AF42C30 => 2026/11/11 16:49:52
两者共同前缀内仅 5 个字节不同，首个差异在 0x138（就是 optional header 的 CheckSum 字段）
sys  : checksum=0x0000F581  secDirVa=0x5A00  secDirSize=1416   ← 尾部 1416 字节 Authenticode 签名
x64  : checksum=0x00007B5F  secDirVa=0x0     secDirSize=0      ← 未签名
```

- 两个文件 **PE 时间戳完全相同（`0x6AF42C30` = 16:49:52）**，大小差 1416 字节 = 签名块大小。
- **`umserialfilter.sys` = `umserialfilter_x64.sys` + Authenticode 签名**，是同一份代码。
- 服务注册表 `ImagePath` 指向的正是这个文件：
  `\??\E:\…\driver\umserialfilter\umserialfilter.sys`
- 签名有效：`Status = Valid`，`CN=UmSerialFilter Test`。
- 二进制内含新代码才有的字符串：UTF-16 `VSerial`×1、`SessionKey`×1、`UmSerialFilter`×5。

**更直接的证据**：`g_accepted` 计数器在运行中真的在递增（每轮 +2）。这个计数器只可能来自当前源码中 `umserialfilter.c:844-847` 新增的那三个变量。**运行中的二进制一定包含新代码。**

> 结论：文档里「运行的是旧二进制、重新部署驱动就能好」的判断是**错的**。按那个建议去做，`rebuild-all.ps1` 会重新生成一个行为完全相同的 `.sys`，0 个端口的问题会一模一样地复现。**不要为此重装驱动。**

### 2.4 三个计数器为什么永远给不出答案

| 计数器 | 累加点 | 实际能反映什么 | 为什么在这里没用 |
|---|---|---|---|
| `g_rejectedType` | 1169 | 打开成功、但 `DeviceType != 0x1b` | 4 个 VSerial 都是真串口，恒为 0 |
| `g_rejectedName` | 1171 | 打开成功、DeviceType 对、但名字前缀不符 | 名字不符其实在 1105 行就 `continue` 了，**根本到不了这里** → 恒为 0，这个计数器实质是死代码 |
| `g_accepted` | 1176 | 打开成功且通过全部闸门 | 确实在涨（每轮 +2），但因为**没有**「打开失败」的计数器，涨不到 4 也无人知晓 |

**结论：这三个计数器设计上就无法诊断本次故障。**

补充：`s[8]`（`AttachedCount`）本身就是最好的诊断量 —— 它一直等于 4，只是调用方没看。

## 3. 根因判断

### 3.1 已证实（有直接证据）

#### 【已证实 1】主根因：`ATTACH_PORTS` 返回「本次新增」被当成「总共」

- **证据 A（代码）**：`umserialfilter.c:1050` 局部 `ULONG attached = 0;`，仅在 `:1209` 自增，`:1228` 返回。已附加分支 `:1217-1219` 不自增。
- **证据 B（实测）**：`discover_probe` 连续 4 次调用，返回恒为 0，而 `s[8]` 恒为 4，`AttachedNames[0..3]` 四个名字全都能取到。
- **证据 C（矛盾）**：同一次 `--driver-test` 里既打印「附加到 0 个 / 未找到任何串口设备」，又捕获 87 条记录并判定 PASS（§1.2）。

#### 【已证实 2】枚举确实在跑，不是「没跑」

- **证据**：`g_accepted` 每次扫描稳定 +2（§1.1），`rejected_type`/`rejected_name` 恒 0。
- 枚举若没跑，`g_accepted` 不会涨。

#### 【已证实 3】运行中的二进制 == 当前源码，不是「旧二进制」

- **证据**：PE 时间戳相同（`0x6AF42C30`）、仅 5 字节差异（CheckSum）、大小差正好 1416 字节的签名块、签名 Valid、二进制含新代码的 `VSerial`/`SessionKey` 字符串、且新计数器在运行中确实在自增（§1.4）。

#### 【已证实 4】采集链路完全正常

- **证据**：`--driver-test` 捕获 87 条 / RX 2724 / TX 65，判定 PASS（§1.2）；`hold_probe` 持句柄期间实测 TX +11、RX +22，并逐条取到记录（见 §3.3 附）。

#### 【已证实 5】`rejected_name` 是死计数器

- **证据**：名字不匹配在 `:1105-1107` 直接 `continue`，而 `g_rejectedName++` 在 `:1171`，只有通过 `:1105` 之后才可能到达。逻辑上不可达。

### 3.2 推测（有强证据但未直接instrumentation证实）

#### 【推测 1】`g_accepted` 每轮只 +2 而非 +4，是因为 COM6/COM7 被 UartAssist 独占，`IoGetDeviceObjectPointer` 打开失败

支持证据链：

1. COM6/COM7 现在打不开：`对端口"COM6"的访问被拒绝` / `COM7` 同样；COM1/COM2 可正常打开。
2. 有 2 个 `UartAssist.exe` 在跑（PID 28596 起于 15:44:55，PID 24532 起于 15:46:17）。
3. **受控实验（决定性，但限于 COM1/COM2）**：我自己用 SerialPort 独占 COM1/COM2，观察 `accepted` 增量：

   | 场景 | accepted 增量 |
   |---|---|
   | 都不占用 | **+2** |
   | 我独占 COM1 | **+1** |
   | 我独占 COM1 + COM2 | **+0** |
   | 全部释放 | **+2** |

   增量随「可打开端口数」精确变化 —— 证明 `accepted` 只在 `IoGetDeviceObjectPointer` **成功**的设备上 +1。
4. 因此 4 个候选里长期只有 2 个可打开（COM1/COM2），`accepted` 稳定 +2；COM6/COM7 被 UartAssist 独占，打开失败，走进无计数分支。

**补充验证（无外部动作时计数器静止）**：间隔 20 秒、不发起任何扫描，`accepted` 保持 81 不变；而每次 `discover_probe` 跑 4 轮扫描，`accepted` 正好 +8（+2×4，实测 57→65→73）。这证明 `accepted` 严格「每个可打开候选 +1 / 每次扫描」，没有其它来源。

> 我没法在核态下打日志验证「COM6 具体是 `STATUS_ACCESS_DENIED` 还是别的 NTSTATUS」，所以严格说这一条是**推测**。但机制本身已由 COM1/COM2 的受控实验证实。

#### 【推测 2】COM6/COM7 在当前状态无法被「重新扫描」新附加

由推测 1 推出：若驱动重新加载（`g_Capture` 被 `RtlZeroMemory` 清零，`:1974`）而 UartAssist 仍占着 COM6/COM7，则首轮扫描只能附加到 COM1/COM2，`AttachedCount` 会是 **2 而不是 4**。
这解释了为什么「重装驱动」这个建议即使执行了也未必达到期望 —— 反而可能让 `AttachedCount` 从 4 掉到 2（因为现在这 4 个是早先端口空闲时附加上的，之后一直保留）。

> 这一条直接影响修复策略，建议按 §5 的「修复后验证」确认。

### 3.3 明确否定的假设

| 假设 | 判定 | 依据 |
|---|---|---|
| 驱动没加载 / 服务没起 | ❌ 否定 | 控制设备可打开、认证成功、`Enabled=1` |
| 枚举根本没跑 | ❌ 否定 | `accepted` 每轮 +2（§1.1） |
| 设备类型不符 | ❌ 否定 | `rejected_type` 恒 0 |
| 名字前缀不符 | ❌ 否定 | 用户态枚举证实 4 个设备名都是 `VSerial8_*`，且 `rejected_name` 恒 0 |
| 运行的是旧二进制 | ❌ 否定 | PE 时间戳/校验和/签名字符串/新计数器自增（§1.4） |
| `SessionKey` 不匹配导致 IOCTL 被拒 | ❌ 否定 | 探针认证返回 true；`ATTACH_PORTS` 返回 `STATUS_SUCCESS`（`ok=1 ret=4`） |

> 附带说明：探针输出里的 `err=6` 是 `DeviceIoControl` **成功后**读的 `GetLastError()`。Win32 的 `DeviceIoControl` 成功时不清 `LastError`，所以这个 6 是无意义残留值，**不是**错误码。特此标注，避免误读。
