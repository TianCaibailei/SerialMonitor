# 驱动兼容性设计说明

> 目标：能用在大多数 Windows 电脑上

---

## 一、已实现的兼容性

### 1. 操作系统版本

| 版本 | 支持 | 说明 |
|---|---|---|
| Windows 7 SP1 | ✅ | 编译期 `NTDDI_VERSION=0x06010000` |
| Windows 8 / 8.1 | ✅ | |
| Windows 10 | ✅ | |
| Windows 11 (含 26200 预览版) | ✅ | 本机实测环境 |
| Windows Server 2008 R2+ | ✅ | 与对应客户端版本同内核 |

**关键**：`NTDDI_VERSION` 和 `WIN32_WINNT`  flooring 到 Win7，意味着：
- 头文件只暴露 Win7 就有的 API
- 不会意外调用 Win8+ 才有的函数（那样在老系统上会加载失败）

### 2. 架构

| 架构 | 状态 | 说明 |
|---|---|---|
| **x64** | ✅ 已编译 | 21,504 字节，覆盖所有现代 PC |
| **x86 (32-bit)** | ⚠️ 构建脚本就绪，缺少内核库 | 见下节 |

### 3. 运行时能力探测

参考驱动在多个地方做运行时探测，我们已对齐：

```c
// 参考驱动 sub_22008 的做法
MmGetSystemRoutineAddress("IoCreateDeviceSecure")      // 缺失则降级
MmGetSystemRoutineAddress("IoValidateDeviceIoControlAccess")
IoIsWdmVersionAvailable(1, 0x20)                        // 版本分支
```

我们的对应实现：

```c
// UmCreateControlDevice 中
static UM_PFN_CREATE_DEVICE_SECURE pfnCreateSecure = NULL;
if (!resolved) {
    RtlInitUnicodeString(&routine, L"IoCreateDeviceSecure");
    pfnCreateSecure = MmGetSystemRoutineAddress(&routine);
    resolved = TRUE;
}
if (pfnCreateSecure != NULL) {
    // 带上 DACL 创建
} else {
    // 降级到普通 IoCreateDevice，靠会话密钥兜底
}
```

**为什么要这样**：
1. `IoCreateDeviceSecure` 在 `wdmsec.lib` 里只有函数指针（`PfnIoCreateDeviceSecure`），直接链接会 `LNK2019`
2. 极老系统上该 API 不存在，动态解析才能优雅降级

## 二、x86 驱动的限制（必须知道）

### 现状

```
WDK NuGet x64 包 (105.7 MB)
  └── c\Lib\10.0.26100.0\km\x64\   ← 有 x64 内核库
  └── c\Lib\10.0.26100.0\km\x86\   ← 不存在

WDK NuGet x86 包 (23.1 MB)
  └── c\Lib\10.0.26100.0\um\x86\   ← 只有用户态库
  └── c\Lib\10.0.26100.0\km\x86\   ← 仍然不存在
```

**结论**：NuGet 分发的 WDK **不包含 x86 内核库**（`ntoskrnl.lib` 等）。

### 影响评估

| 场景 | 是否需要 x86 驱动 |
|---|---|
| Windows 10/11 64 位 | ❌ 不需要，x64 驱动即可 |
| Windows 7/8.1 64 位 | ❌ 不需要 |
| **Windows 7/8.1/10 32 位** | ✅ 需要 |

**实际情况**：
- 2010 年后的 PC 几乎都是 64 位系统
- 32 位 Windows 现在主要用于：老旧工控机、嵌入式设备、部分行业专用机
- 串口监控的典型场景（PLC、仪表、老设备对接）**确实会碰到 32 位工控机**

### 获取 x86 内核库的两个方案

#### 方案 A：安装完整 WDK MSI（推荐，但要解决下载问题）

完整 WDK MSI 包含 `Lib\10.0.26100.0\km\x86`。之前安装失败是因为 bootstrapper 下载器不稳，可以：

1. 从微软官网下载 **WDK 完整 ISO**（约 800MB）
2. 挂载后从 `Installers\` 目录取 x86 payload
3. 或用其他网络环境执行 `wdksetup.exe`

#### 方案 B：只用 x64 驱动（当前建议）

**这不影响绝大多数用户**：
- 安装包只放 x64 驱动
- 在 32 位系统上安装时，检测到架构不匹配 → 自动降级为**用户态 hook 模式**
- 用户态 hook 已实现且可用（有"先附加后开端口"的限制）

安装包逻辑：
```powershell
$is64 = [Environment]::Is64BitOperatingSystem
if ($is64) {
    # 安装 UmSerialFilter x64 驱动
} else {
    # 提示：32 位系统使用用户态模式（功能略受限）
}
```

## 三、驱动与软件的配对（安全）

### 参考驱动的做法（不采用）

逆向确认：`ComDrv12x64.sys` 的安全描述符 SDDL 是

```
D:P(A;;GA;;;WD)
      ↑    ↑
      |    └── WD = Everyone
      └─────── GA = Generic All（全部权限）
```

**含义：任何进程都能完全访问这个驱动**——包括读取所有串口数据。
这是明显的安全缺陷，我们**不复制**。

### 我们的做法（两层）

#### 第一层：设备 ACL

通过 `IoCreateDeviceSecure` 设置 SDDL：

```
D:P(A;;GA;;;SY)(A;;GA;;;BA)(A;;GRGW;;;BU)
     │         │         │
     │         │         └── BU = Users，只给读写
     │         └──────────── BA = Administrators，全部
     └────────────────────── SY = LocalSystem，全部
```

- `D:P` 中的 `P` = **Protected**，不从 `\Device` 继承任何 ACE
- 普通用户能打开设备（否则无法运行监控软件）
- 但只有 SYSTEM/Administrators 有完整权限

#### 第二层：会话密钥握手

驱动加载时生成**每启动一次就变化的 16 字节密钥**，写入：
```
HKLM\Software\UmSerialFilter\SessionKey
```

- 普通用户**无法写入** HKLM（需要管理员）
- 用户态读取这个密钥后，第一个 IOCTL 必须是 `IOCTL_UM_AUTHENTICATE` 并携带密钥
- **认证通过前，其他所有 IOCTL 返回 `STATUS_ACCESS_DENIED`**

```c
// 驱动侧
if (code == IOCTL_UM_AUTHENTICATE) {
    if (!UmKeyMatches(buf)) { status = STATUS_ACCESS_DENIED; }
    else { dctx->Flags |= UM_CTX_AUTHENTICATED; }
}
if ((dctx->Flags & UM_CTX_AUTHENTICATED) == 0) {
    return STATUS_ACCESS_DENIED;   // 所有其他 IOCTL
}
```

#### 第三层：IOCTL 访问位校验

```c
if (!IoValidateDeviceIoControlAccess(Irp, FILE_READ_ACCESS)) {
    return STATUS_ACCESS_DENIED;
}
```

确保只读句柄不能调用写类 IOCTL（`SET_TARGET`、`ATTACH_PORTS`）。

### 效果对比

| 攻击面 | 参考驱动 | 我们的驱动 |
|---|---|---|
| 任意进程读串口数据 | ❌ 可以 | ✅ 需要密钥 |
| 任意进程改捕获策略 | ❌ 可以 | ✅ 需要密钥 |
| 低完整性进程打开设备 | ❌ 可以 | ⚠️ 需 Users 组（沙箱进程通常不在） |
| 只读句柄调用写 IOCTL | ❌ 可以 | ✅ 被拒 |
| 内核地址泄漏 | ❌ 回传 PDO 指针 | ✅ 回传自增 ID |

## 四、关闭/释放的完整清理

你说"尤其是涉及软件关闭相关的释放"，这是最容易出问题的地方。完整清单：

### 监控软件退出时

| 资源 | 处理 |
|---|---|
| 控制设备句柄 | `IRP_MJ_CLEANUP` → `IRP_MJ_CLOSE` → `OpenCount--` |
| 最后一个句柄关闭 | `Enabled = 0`，停止捕获（不再消耗 CPU/内存） |
| 已附加的过滤设备 | **保留**，下次打开可立即恢复捕获 |
| 队列中的记录 | 保留（上限 512 条），下次打开可读 |

### 驱动卸载时（`sc stop`）

| 资源 | 处理 |
|---|---|
| PnP 通知注册 | `IoUnregisterPlugPlayNotification` |
| 符号链接 | `IoDeleteSymbolicLink` |
| 控制设备 | `IoDeleteDevice` |
| **每个过滤设备** | `IoDetachDevice` + `IoDeleteDevice` + `ObDereferenceObject(PDO)` |
| **槽位表** | 逐项清空（`SlotUsed[]`、`Attached[]`、`AttachedNames[]`） |
| **队列** | 循环排空（`ExFreeToNPagedLookasideList` 每个 item） |
| **Lookaside 列表** | 排空后才 `ExDeleteNPagedLookasideList` |
| 名字字符串 | `ExFreePoolWithTag`（每个 slot 一份） |

**关键**：`ExDeleteNPagedLookasideList` 不会释放仍被借出的条目。
不排空队列就删除，最多泄漏 512 × 4KB ≈ 2MB 非分页内存。

### 单个串口设备拔出时

| 资源 | 处理（`UmRemoveComplete`） |
|---|---|
| 槽位 | `UmFreeSlotResources(ctx->Index)` —— 释放名字、清位图 |
| 挂接关系 | `IoDetachDevice` |
| PDO 引用 | `ObDereferenceObject` |
| 过滤设备对象 | `IoDeleteDevice` |

**这是上一轮的严重 bug**：原来只 `IoDeleteDevice`，槽位永不回收，
插拔 64 次后 `Attached[]` 满，之后再插入的串口**静默不被监控**。

## 五、构建命令

```powershell
cd E:\Documents\MonitorAnything\MonitorAnything\driver

# 默认：x64 + x86，Win7 起
powershell -File build-driver.ps1 -Source umserialfilter\umserialfilter.c

# 只编译 x64（当前环境可行）
powershell -File build-driver.ps1 -Source umserialfilter\umserialfilter.c -Arch x64

# Windows 10 起步
powershell -File build-driver.ps1 -Source umserialfilter\umserialfilter.c -Os win10
```
