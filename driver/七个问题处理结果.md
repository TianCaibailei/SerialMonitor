## ✅ 1. 通道列显示 COM 号

### 改动

通道列原来显示设备短名（`VSerial8_2`）或 `端口2`，现在显示 **COM 号**：

| 之前 | 现在 |
|---|---|
| `端口2` | `COM6` |
| `VSerial8_2` | `COM6` |

### 实现

启动捕获时从注册表读一次映射：

```
HKLM\HARDWARE\DEVICEMAP\SERIALCOMM
  \Device\VSerial8_2  →  COM6
  \Device\VSerial8_3  →  COM7
```

存进 `drv_com`，创建通道时用它命名。没有 COM 号的设备退回显示设备短名。

端口勾选列表里同时显示两者：`COM6  (VSerial8_2)`。

## ✅ 4. 暂停监视无效 / 清空不归零

### 4a. 暂停无效

**原因**：`s.running = false` 只改了标记，但 `drain_driver` 仍然把驱动数据写进会话。

**修复**：在 `drain_driver` 里检查会话状态：

```rust
if let Some(s) = self.sessions.get(sess_idx) {
    if !s.running {
        continue;   // 暂停的会话不再增长
    }
}
```

> 捕获线程仍然继续排空驱动队列（否则队列会溢出），只是不写入暂停的会话。

### 4b. 清空不归零

**原因**：`clear()` 只清了 `rows`，没重置 `seq`，所以序号从上次的值继续。

**修复**：

```rust
pub fn clear(&mut self) {
    self.rows.clear();
    self.selected = None;
    self.find_pos = 0;
    self.seq = 0;        // ← 序号归零
    self.bytes_rx = 0;   // ← 字节计数归零
    self.bytes_tx = 0;
    self.rate.clear();
    self.bufs.clear();
}
```

## ✅ 5. 状态栏进程数刷新太累赘

### 原因

自动附加服务每 10 个 tick 就打一条日志：

```
已知=320 候选=254 新进程=UosClient.exe:8404
```

这些数字每秒变化，状态栏不停闪烁，而且对用户没有意义。

### 修复

改为**只在发现新进程时**才记录：

```rust
// 原来是：if ticks % 10 == 1 || !fresh.is_empty()
// 现在是：if !fresh.is_empty()
```

现在只有真正附加进程时才会显示：

```
已附加进程 UosClient.exe (PID 8404)
```

平时状态栏保持安静。

## ✅ 6. 32 位注入失败（已根治）

### 真实错误

```
注入失败: 32位注入器失败: 诊断: LoadLibraryW=0x7ffe28cbf6c0 ...
LoadLibraryW 返回 NULL (GetLastError=0x6)
```

`0x7ffe28cbf6c0` 是 **64 位地址** —— 说明运行的是 64 位注入器，向 32 位进程调用必然失败。
`GetLastError=0x6` = `ERROR_INVALID_HANDLE`。

### 根因（第三次出现，这次根治）

注入器原来放在 `app/src/bin/universal_injector_x86.rs`，
`cargo build --release` 会把它**按主机架构（x64）编译**并覆盖部署的 32 位文件。

之前两次修复都是手动重新部署，但**下一次 `cargo build --release` 又会覆盖**。

### 根本修复

把注入器**移出主 crate**，成为独立 crate：

```
app/x86_injector/
  Cargo.toml     ← 独立 package
  src/main.rs
```

主 `Cargo.toml` 的 workspace：

```toml
members = ["hook", "x86_injector"]
```

现在 `cargo build --release`（主程序）**完全不会碰它**，只有显式指定
`--target i686-pc-windows-msvc -p universal_injector_x86` 才会构建。

### 构建脚本强制校验架构

`build-gui.ps1` 现在会：

1. 用 `--target i686-pc-windows-msvc` 显式交叉编译注入器
2. 部署后**读取 PE 头校验架构**
3. 如果不是 x86 直接抛错

```
=== 产物 ===
  universal_monitor.exe          x64   5,068,288 字节
  universal_injector_x86.exe     x86     210,432 字节
PASS: 编译完成
```

## ⚠️ 7. 串口数据顺序问题（暂时保留）

### 你观察到的现象

```
A 串口发送 → 监视到：
  1. B 串口读操作（部分内容）
  2. A 的写操作
  3. B 串口读取剩余内容
```

### 这是虚拟串口的正常行为

ELTIMA 虚拟串口是**成对**的（COM6 ⟷ COM7）。数据流向：

```
程序A 写 COM6
   ↓
ELTIMA 驱动把数据传给 COM7
   ↓
程序B 从 COM7 读（分多次：先读到一部分，再读到剩余）
```

驱动在 `IRP_MJ_READ/WRITE` **完成时**捕获，所以看到的顺序就是**实际完成顺序**：

1. B 在 COM7 上的第一次读完成（拿到前几个字节）
2. A 在 COM6 上的写完成
3. B 在 COM7 上的第二次读完成（拿到剩余字节）

**这不是 bug，是真实的执行顺序。** 参考程序大概率也是这个表现。

### 可以改善的地方

`Session` 里有 `merge_ms` 合并机制（同方向、时间窗口内的多条记录合并成一行），
但 `ingest_driver` 目前绕过了它（为了保证驱动数据原样呈现）。

如果你希望把「B 的两次读」合并成一行，我可以在驱动捕获路径也启用合并。
需要你确认：

- **保持原样**（每条 IRP 完成一条记录，最真实）
- **启用合并**（同端口同方向、间隔 < N 毫秒的记录合成一行，更易读）

用 `build-gui.ps1` 编译 GUI 就能直接测试。
