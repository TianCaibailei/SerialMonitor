> 2026-11-11 · 已编译签署前状态：**20,480 字节**
> 本次修改基于对参考驱动 `ComDrv12x64.sys` 的逐函数汇编还原

---

## 一、这次找到的 5 个真实缺陷

### 缺陷 1（致命）：`ZwQueryDirectoryObject` 参数顺序写反

```c
// 错误（之前所有版本）
ZwQueryDirectoryObject(handle, buf, len,
    first,     // ← 传给了 ReturnSingleEntry
    TRUE,      // ← 传给了 RestartScan，恒为 TRUE
    &context, &retLen);

// 正确
ZwQueryDirectoryObject(handle, buf, len,
    TRUE,      // ReturnSingleEntry
    first,     // RestartScan：仅首次 TRUE
    &context, &retLen);
```

**后果**：`RestartScan` 永久为 TRUE → 每次都从头枚举同一条 → **无限循环 → IOCTL 永不返回**。

这就是 `ATTACH_PORTS` 卡死、`reader` 超时的**真正原因**。之前我两次试图修这个循环都治标不治本，因为根子是参数位置传错。

### 缺陷 2（致命）：函数未声明导致 x64 指针截断

```c
ObReferenceObjectByName(...)   // ← 隐式 int 返回
ZwOpenDirectoryObject(...)     // ← 隐式 int 返回
ZwQueryDirectoryObject(...)    // ← 隐式 int 返回
```

在 x64 上，隐式 `int` 返回会把 **64 位指针截断成 32 位**。编译器只给 `warning C4013`，不会报错。

**这是最典型的"静默蓝屏"来源**。

修复：显式声明三个函数的完整原型（参数顺序已按 `ntifs.h` 核对）。

### 缺陷 3（致命）：设备名用子串匹配 → 挂到别人的设备 → 蓝屏

之前 `fragments` 表里有 `"vcp"`、`"vser"` 这类短片段，会命中 VPN、虚拟化、DLP 安全软件的设备。

`IoAttachDeviceToDeviceStack` 把我们的过滤器插入对方 IRP 链 → 对方收到被改写的 IRP → 访问违例 → **`0x3B` 蓝屏**（报告指向 `DocPrismX64.sys`，但污染是我们造成的）。

修复：**删除整个 `UmLooksLikeSerialPort` 和 `fragments` 表**，改为只做**前缀匹配**，且只有两个命名空间：

```c
L"Serial"
L"VSerial"
```

**依据**：参考驱动 `sub_127b0` / `sub_128e8` 的汇编里只比较两个字符串（地址 `0x13440` 和 `0x13460`），从不做子串匹配。

### 缺陷 4：挂接标志设置顺序错误

参考驱动 `sub_11308` 的精确顺序：

```
0x1133e  IoCreateDevice
0x1134c  复制 DO_BUFFERED_IO
0x11359  复制 DO_DIRECT_IO
0x11366  复制 FILE_DEVICE_SECURE_OPEN
0x1137b  filter->Flags |= DO_POWER_PAGABLE
0x11383  IoAttachDeviceToDeviceStack    ← 挂接在设置标志之后
0x113df  filter->Flags &= ~DO_DEVICE_INITIALIZING
```

我们原来是**先挂接再设标志**，存在窗口期：下层已经能收到 IRP，但我们的过滤设备标志还没就绪。

修复：严格按上方顺序。

### 缺陷 5：`ObReferenceObjectByName` 使用不当

参考驱动 `sub_1140c` 的做法是：

```c
IoGetDeviceObjectPointer(name, 0x1f01ff, &fileObj, &devObj);
if (success) {
    ObDereferenceObject(fileObj);   // 立即释放文件对象
    // 后续用 devObj
}
```

我们之前用 `ObReferenceObjectByName`（一个未声明的函数），既有截断风险，又跳过了参考驱动的引用管理。

修复：两条路径（扫描 + 热插拔）都改为 `IoGetDeviceObjectPointer` + 立即 `ObDereferenceObject(fileObj)` + 显式 `ObReferenceObject(devObj)` 自持引用。

## 二、本机验证的匹配范围

查询 `HKLM\HARDWARE\DEVICEMAP\SERIALCOMM`：

```
\Device\VSerial8_0 → COM1
\Device\VSerial8_1 → COM2
\Device\VSerial8_2 → COM6
\Device\VSerial8_3 → COM7
```

你的串口全部是 **ELTIMA 虚拟串口**，路径以 `\Device\VSerial8_` 开头。

**新的前缀匹配恰好覆盖这 4 个，不会碰任何其他设备。**

## 五、诚实说明：我的判断依据

这次我**不再靠试错**，而是把每个改动都锚定在参考驱动的汇编证据上：

| 改动 | 证据 |
|---|---|
| 前缀匹配只有 Serial/VSerial | `sub_127b0` / `sub_128e8` 只比较 `0x13440` 和 `0x13460` |
| 挂接标志顺序 | `sub_11308` 逐条汇编 |
| `IoGetDeviceObjectPointer` + 立即 `ObDereferenceObject` | `sub_1140c` 逐条汇编 |
| `DO_POWER_PAGABLE = 0x2000` | `wdm.h` 定义 + `bts [rax+0x30], 0xd` |
| 设备对象字段偏移 | `wdm.h` 第 31960 行结构定义 |

**唯一仍不确定的**：参考驱动遍历的是 `OBJECT_DIRECTORY` 内部散列表（未文档化结构），我用的是 `ZwQueryDirectoryObject`（文档化 API）。但这是**更安全**的选择，且现在已经用对了参数。

在崩溃原因上，我现在有三个**独立且都有证据**的修复（参数顺序、隐式声明、子串匹配）。即使其中一个不是主因，另外两个也足以避免已知的崩溃路径。
