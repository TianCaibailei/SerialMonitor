## 问题 1：慢一拍 —— 你的判断是对的，不是刷新频率

我用实测推翻了自己上一轮的结论。

### 实测数据

```
[16:14:47.832] 发送第1条 AAA111;
[16:14:49.840] 发送第2条 BBB222;
[16:14:51.850] 发送第3条 CCC333;

驱动捕获记录：
[TX] AAA111;   ← 第1条立即被捕获
[TX] BBB222;   ← 第2条立即被捕获
[TX] CCC333;   ← 第3条立即被捕获
```

**驱动和数据读取都是实时的**，没有延迟。所以刷新频率不是原因（我上轮改成 16ms 是错的修正）。

### 但真正的根因被另一个发现掩盖了

诊断时发现：**驱动现在附加到 0 个串口设备**。

```
driver-test: 附加到 0 个串口设备
```

这意味着 GUI 里那些"延迟"的数据，很可能来自**旧的、状态异常的挂接**，而不是实时的正确捕获。

### 已做的改进

1. **回退了 16ms 的想法**，改为让驱动侧直接提供精确时间戳（Unix 毫秒），GUI 按记录的真实时间显示，不再依赖重绘时机。
2. **新增诊断计数器**（见下），下次能直接看出为什么附加 0 个。

## 问题 2：端口过滤 —— 已按你的建议实现

### 设计

| 项 | 实现 |
|---|---|
| 默认行为 | **监视所有串口**（`drv_watch` 为空 = 不限制） |
| 过滤方式 | 在「驱动捕获设置」对话框里**勾选/取消勾选** |
| 显示格式 | `COM6  (VSerial8_2)` —— COM 号在前，设备名在后 |
| 排序 | 按 COM 号排序，符合用户习惯 |
| 全选 | 提供「全选」按钮一键恢复 |

### COM 号从哪来

从注册表读取 Windows 自己维护的映射：

```
HKLM\HARDWARE\DEVICEMAP\SERIALCOMM
  \Device\VSerial8_2  →  COM6
  \Device\VSerial8_3  →  COM7
```

新增 `driver::com_names()` 读取该键，UI 用"COM6"显示，内部用设备短名匹配驱动数据。

### 效果

取消勾选 COM7 后，COM7 的数据不再进入表格（驱动的数据仍在管道里，只是 GUI 丢弃）。

## 新发现的问题：驱动附加到 0 个串口

### 现象

```
driver-test: 已连接驱动
driver-test: 附加到 0 个串口设备
```

之前成功时是 **4 个**。

### 原因

当前运行的驱动是 **15:43 编译的 23,944 字节版本**，
而最新代码是 **23,040 字节**。中间我改动过匹配逻辑（前缀匹配 + 设备类型闸门），
**运行中的是旧二进制**，行为与新代码不一致。

### 已加的诊断

驱动新增 3 个计数器，通过 `IOCTL_UM_GET_STATS` 暴露：

| 计数器 | 含义 |
|---|---|
| `rejected_type` | 因 **DeviceType 不是 FILE_DEVICE_SERIAL_PORT** 被拒 |
| `rejected_name` | 因 **名字不匹配 Serial/VSerial** 被拒 |
| `accepted` | 通过闸门 |

设置对话框里会直接显示：

```
扫描结果：类型不符 12 个，名称不符 3 个。
名称不符说明串口设备名不在 Serial/VSerial 命名空间内。
```

**这样下次附加 0 个时，能立刻知道是哪一类拒绝。**

## 关于"慢一拍"的后续

部署新驱动后，如果数据仍然延迟，我需要你提供更精确的信息来定位：

1. 发送第 1 条后，**等 10 秒**，数据会出现吗？
   - 会 → 是刷新/重绘问题
   - 不会 → 是数据流问题

2. GUI 状态栏的 `行数` 数字，在发送后是否立即增加？
   - 增加但表格没刷新 → 渲染问题
   - 不增加 → 数据没进来

这两个答案能直接区分问题层次。
