# 串口被占用 / 程序卡死：原因与恢复步骤

> 2026-11-11 · 已定位为驱动的三个严重 bug，代码已修复

## 一、症状回顾

| 现象 | 你的描述 |
|---|---|
| 端口全被占用 | “几乎所有串口都无法打开，提示端口被占用” |
| 程序卡死 | “gui 程序卡住，任务管理器都无法结束” |
| reader 无输出 | “提示已连接过滤驱动，但迟迟没有后续输出，卡住无法关闭” |

三个症状是**同一个根因**的三个侧面。

---

## 二、根因（已修复）

### Bug 1：`IRP_MJ_CREATE` 被控制设备处理器截获 ← 主因

Windows 内核给同一驱动的**所有设备对象共用一份分发函数表**（`DriverObject->MajorFunction`）。

我原来的代码把 `IRP_MJ_CREATE` 指向了 `UmControlCreate` —— 这个函数专门给控制设备用，
它**直接完成请求，不转发**：

```c
static NTSTATUS UmControlCreate(PDEVICE_OBJECT DeviceObject, PIRP Irp) {
    Irp->IoStatus.Status = STATUS_SUCCESS;   // ← 自己答了
    IoCompleteRequest(Irp, IO_NO_INCREMENT);
    return STATUS_SUCCESS;
}
```

于是串口过滤设备也用了这个函数。当任何程序 `CreateFile("\\\\.\\COM6")` 时：

```
应用程序 → 我们的过滤设备 → UmControlCreate 直接返回 SUCCESS
                             ↑ 串口驱动根本没收到这个 IRP
```

**结果**：
- 打开「成功」了，但串口驱动从未初始化该端口
- 后续读写全部失败或挂起 → **端口看起来被占用**
- 读操作等一个永远不会到来的完成 → **程序卡死**

### Bug 2：完成例程的栈位置错误

```c
// 错误写法
IoSkipCurrentIrpStackLocation(Irp);          // 下层复用我们的栈位
stack->CompletionRoutine = ...;              // 又往同一个栈位写 → 覆盖
```

`IoSkipCurrentIrpStackLocation` 的语义是「让下层**复用**我的栈位」，
之后往同一位置写完成例程会破坏下层看到的数据。

正确做法是 `IoCopyCurrentIrpStackLocationToNext` + 往 `IoGetNextIrpStackLocation` 写。

### Bug 3：设备移除时的 use-after-free

```c
NTSTATUS status = IoCallDriver(ctx->Lower, Irp);
IoDetachDevice(ctx->Lower);
IoDeleteDevice(DeviceObject);     // ← 下层可能还没完成
```

`IoCallDriver` 可能异步返回，此时设备对象（以及 IRP 的栈位置内存）已被释放，
下层后续访问就是访问已释放内存。正确做法是用完成例程延迟拆卸。

## 三、立即恢复步骤（串口现在不可用）

### 第 1 步：重启电脑（推荐，最彻底）

驱动正在运行且占着端口。重启会卸载它。

重启后**不要**再运行 `setup-driver.ps1`，先按下面重新编译。

### 第 2 步（不想重启的话）：管理员运行应急脚本

```powershell
# 管理员 PowerShell
cd E:\Documents\MonitorAnything\MonitorAnything\driver
powershell -ExecutionPolicy Bypass -File fix-ports.ps1
```

它会：结束卡死进程 → 停止驱动 → 逐个验证串口能否打开。

> 如果驱动处于 `START_PENDING`，脚本会告诉你只能重启。

### 第 3 步：重新编译修复后的驱动

```powershell
cd E:\Documents\MonitorAnything\MonitorAnything\driver

# 先删掉旧服务（重启后这一步一定能成功）
sc delete UmSerialFilter

# 编译
powershell -ExecutionPolicy Bypass -File build-driver.ps1 -Source umserialfilter\umserialfilter.c
```

预期输出：
```
PASS: 驱动编译成功 ...umserialfilter.sys (16,384 字节)
```

### 第 4 步：签名

```powershell
& 'C:\Program Files (x86)\Windows Kits\10\bin\10.0.19041.0\x64\signtool.exe' `
    sign /s My /sha1 89504FECC3504FB928B20D7034A82BF91F71423A /fd SHA256 `
    umserialfilter\umserialfilter.sys
```

### 第 5 步：安装并验证

```powershell
powershell -ExecutionPolicy Bypass -File setup-driver.ps1
```

**关键验证（务必先做这一步）**：

```powershell
# 驱动启动后，先确认端口正常，再谈捕获
$p = New-Object System.IO.Ports.SerialPort('COM6',9600)
$p.Open(); $p.Close()
"COM6 可以正常打开"
```

- **如果 COM6 能正常打开** → 修复成功，继续测捕获
- **如果打不开** → 说明还有问题，请把错误信息发我

### 第 6 步：验证捕获

```powershell
# 终端 1：启动 reader
E:\Documents\MonitorAnything\MonitorAnything\driver\umfilter_reader\umfilter_reader.exe 20

# 终端 2（或串口助手）：正常打开 COM6 收发数据
```

预期：reader 打印 `驱动已附加到 N 个串口设备`，然后出现 `[TX]` / `[RX]` 记录。

## 四、修复对照表

| Bug | 修复方式 |
|---|---|
| CREATE 被截获 | 共享入口按 `UmIsControlDevice()` 分流：控制设备自己处理，过滤设备原样转发 |
| 完成例程栈错位 | `IoCopyCurrentIrpStackLocationToNext` + 写 `IoGetNextIrpStackLocation` |
| 移除时 UAF | 新增 `UmRemoveComplete` 完成例程，延迟拆卸 |
| 电源状态机 | 去掉无条件的 `PoStartNextPowerIrp` |
| 空指针 | PnP/Power 增加 `Lower == NULL` 保护 |

---

## 五、为什么之前没发现

上一轮的验证只做到「驱动能 RUNNING」就停了，**没有验证「端口仍能正常使用」**。

这次补上了这条，并且写进了 `setup-driver.ps1` 的建议流程里：
**先验证端口可用，再验证捕获可用**。

这是被动监控的底线要求 —— 监控软件绝不能影响业务程序使用串口。
