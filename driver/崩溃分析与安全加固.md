## 二、根因：我们的驱动挂到了别人的设备上

### DocPrismX64.sys 是什么

```
C:\Program Files (x86)\DocProtect\engine\mirror\DocPrismX64.sys
```

这是 **DocProtect 文档透明加密/DLP 产品**的内核驱动（文件系统过滤）。
也就是你之前遇到的"编译产物被自动加密"的同一套软件。

### 我们的驱动做了什么导致它崩溃

我们的扫描逻辑（`UmAttachAllPorts`）遍历 `\Device` 目录，
对**名字匹配串口特征**的设备执行 `IoAttachDeviceToDeviceStack` 挂接。

问题出在**名字匹配太宽松**：

```c
static const PCWSTR fragments[] = {
    L"Serial", L"serial",
    L"VCP", L"vcp",        // ← 危险
    L"vser", L"Vser",      // ← 危险
    ...
};
```

`"vcp"` 和 `"vser"` 这些短片段会命中**非串口设备**：
- VPN 产品的虚拟设备
- 虚拟化/容器设备
- DLP / 安全软件的自定义设备对象
- 其他 `\Device\VCP*`、`\Device\vser*` 命名空间

### 为什么这会导致别的驱动崩溃

```
IoAttachDeviceToDeviceStack(filter, target)
```

这个调用会把**我们的过滤设备插入到目标设备的 IRP 处理链前面**。之后：

1. 应用向那个设备发 IRP
2. I/O 管理器先调用**我们的**分发函数
3. 我们改写 IRP 的 stack location（`IoCopyCurrentIrpStackLocationToNext`）
4. 转发给真正的驱动（如 DocPrismX64.sys）
5. 它拿到的是**被我们改过的 IRP 结构**
6. 它的代码按自己的假设解析 → **访问违例 → 蓝屏**

**崩溃报告指向 DocPrismX64.sys，因为栈帧在它里面，但污染是我们在它之前造成的。**

### 为什么重启后立刻又崩

驱动被设置为 `demand start`，但**服务残留** + 系统启动时其他程序（DocProtect 的 `DocMirror.exe` 等）立即打开它们的设备 → 我们的过滤器立刻介入 → 再次崩溃。

## 三、已实施的加固

### 加固 1：双重安全闸门（核心）

新增 `UmIsSafeSerialTarget()`，**四项检查全部通过才允许挂接**：

```c
static BOOLEAN UmIsSafeSerialTarget(PDEVICE_OBJECT Target, PCUNICODE_STRING Name)
{
    // 1. 必须真的是设备对象
    if (Target->Type != IO_TYPE_DEVICE) return FALSE;

    // 2. DeviceType 必须是 FILE_DEVICE_SERIAL_PORT (0x1b)
    //    ← 这是权威判据。名字可以骗人，设备类型不能。
    if (Target->DeviceType != FILE_DEVICE_SERIAL_PORT) return FALSE;

    // 3. 不能是我们自己的控制设备
    if (Target == g_ControlDevice) return FALSE;

    // 4. 名字仍需匹配串口家族
    if (Name != NULL && !UmLooksLikeSerialPort(Name)) return FALSE;

    return TRUE;
}
```

**第 2 条是关键**：串口驱动必须声明 `FILE_DEVICE_SERIAL_PORT`。
无论设备名字里有没有 "vcp"、"serial"，只要类型不对，我们**绝不碰它**。

### 加固 2：热插拔路径同样受保护

```c
// UmHotplugAttachLink 中
if (!UmIsSafeSerialTarget(devObj, link)) {
    ObDereferenceObject(devObj);
    return STATUS_DEVICE_NOT_CONNECTED;
}
```

### 加固 3：热插拔不再打开设备

`IoGetDeviceObjectPointer` → `ObReferenceObjectByName`，不阻塞、不打开端口。

## 六、教训

这次事故暴露了三个层面的问题：

### 1. 技术上：拿名字当身份

用设备名片段判断"是不是串口"是**不可靠的**。名字是字符串，
任何驱动都可以起任何名字。真正的身份是 `DeviceType`。

**修复原则**：能用结构化属性判断的，绝不用字符串匹配。

### 2. 设计上：挂接他人设备的代价

`IoAttachDeviceToDeviceStack` 是一个**高权限、高破坏性**的操作。
挂错了不是"没效果"，而是**让被挂的驱动崩溃**。

**修复原则**：挂接前必须证明目标正确，失败时宁可不挂。

### 3. 流程上：验证顺序

前一轮我一直在追"为什么捕获不到数据"，反复改动挂接逻辑，
但**没有先验证"挂接本身是否安全"**。

`verify-driver.ps1` 里第 2 步（串口可打开）只检查了串口，
没有检查"系统其他驱动是否受影响"。

**改进**：未来应该在测试机上先跑，或至少在改动挂接逻辑后
观察系统事件日志是否有新的驱动错误。
